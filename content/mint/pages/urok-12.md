## Коротко

Правила ЛР7 (с. 3-4) - це **розробка через тести** (test-driven): спершу опис і тести, потім код.

```text
1. Коментар на початку файлу: список функцій і що кожна робить
2. Заготовка кожної функції: сигнатура з типами + докстрінг + raise NotImplementedError
3. Щонайменше 5 doctest у кожній: типові і граничні випадки (порожній вхід, мінімум, вироджене)
4. python3 -m doctest файл.py  → усі тести падають з NotImplementedError  (це нормально!)
5. Пишеш тіло однієї функції → її тести зеленіють → наступна
```

**`NotImplementedError`** - вбудований виняток «ще не написано». `raise` - інструкція «кинути виняток». Заготовка з ним
одразу запускається, але кожен виклик чесно каже, що функції ще нема.

| Що | Команда |
|---|---|
| запустити тести, побачити лише провали | `python3 -m doctest lr7_1.py` |
| підсумок | `python3 -m doctest -v lr7_1.py \| tail -n 3` |
| скільки рядків `>>>` у файлі | `grep -c ">>>" lr7_1.py` |
| чи не лишилось заготовок | `grep -n NotImplementedError lr7_*.py` |
| подати ввід без набору | `printf '130\n' \| python3 lr7_1.py` |

Один файл - одне завдання: `lr7_1.py`, `lr7_2.py`, `lr7_3.py`.

**1.** Зріз з кроком вилучає **позиції**, а не значення. Що надрукує?

```python
letters = list("abcdefghij")
del letters[2::3]
print(letters)
```

<details markdown="1"><summary>Відповідь</summary>

```text
['a', 'b', 'd', 'e', 'g', 'h', 'j']
```

`[2::3]` - позиції 2, 5, 8 (рахуємо з нуля), тобто кожен 3-й елемент, починаючи з третього: `c`, `f`, `i`. Саме так
на с. 1 описано `del lst[s-1::s]` - «кожен s-й з позиції s-1».
</details>

**2.** Вирівнювання праворуч. Що надрукує?

```python
print("|".join(f"{number:>4}" for number in [5, 50, 500]))
```

<details markdown="1"><summary>Відповідь</summary>

```text
   5|  50| 500
```

`:>4` - ширина 4, притиснути праворуч, зліва пробіли. Ширину можна взяти зі змінної: `f"{number:>{width}}"` (с. 3).
</details>

**3.** Що надрукує?

```python
import math

print(0.1 + 0.2 == 0.3, math.isclose(0.1 + 0.2, 0.3))
```

<details markdown="1"><summary>Відповідь</summary>

```text
False True
```

float зберігає 0,1 і 0,2 з крихітною похибкою, і сума не точно 0,3. У режимі а) завдання 2 точки можуть бути
дробовими - тоді «скалярний добуток = 0» перевіряй з допуском (`math.isclose(..., 0, abs_tol=1e-9)`), а не `==`.
У режимі б) координати цілі, і `== 0` точне.
</details>

**4.** Скільки трійок з 6 точок і скільки четвірок зі 100?

```python
import itertools
import math

print(len(list(itertools.combinations(range(6), 3))), math.comb(100, 4))
```

<details markdown="1"><summary>Відповідь</summary>

```text
20 3921225
```

C(6, 3) = 20, C(100, 4) = 3 921 225 - майже 4 мільйони (у PDF, с. 3, «близько 3 мільйонів»). Для режиму в) з N = 4
точок 18, четвірок C(18, 4) = 3060 - це швидко.
</details>

Назви функцій тут - лише приклад; декомпозицію вигадуєш сам, але кожна функція - одна задача. Функція, що **друкує**,
погано тестується doctest-ом; краще хай повертає рядок, а друкує `main`.

**Як тестувати введення.** Функцію, що сама викликає `input()`, doctest перевірити не може: під час тесту вона
чекатиме клавіатуру (pytest без `-s` падає з `reading from stdin while output is captured`). Тому ділимо на дві:
**чиста** функція бере вже введений **рядок** і повертає число або кидає `ValueError` - її легко покрити 5 doctest-ами;
а тонка `main()` лише робить `input()` і `print` - у ній нема чого тестувати. Приклад на **іншій** задачі (скільки
квадратів надрукувати), файл `kvadraty.py`:

```python
def parse_count(text: str) -> int:
    """Кількість з введеного рядка: ціле число, не менше 1.

    >>> parse_count("5")
    5
    >>> parse_count(" 12 ")
    12
    >>> parse_count("1")
    1
    >>> parse_count("0")
    Traceback (most recent call last):
    ...
    ValueError: потрібно ціле число від 1, а не 0
    >>> parse_count("п'ять")
    Traceback (most recent call last):
    ...
    ValueError: invalid literal for int() with base 10: "п'ять"
    """
    count = int(text)
    if count < 1:
        raise ValueError(f"потрібно ціле число від 1, а не {count}")
    return count


def main() -> None:
    count = parse_count(input("Скільки квадратів? "))
    for number in range(1, count + 1):
        print(number, number * number)


if __name__ == "__main__":
    import doctest

    doctest.testmod()
    main()
```

> **Нове тут:**
>
> - `python3 -m doctest`: `-v` - докладно: кожен приклад (Trying, Expecting, ok) і підсумок «N passed and M failed».
> - `printf` - друкує текст за шаблоном; \n - Enter. Назва: print formatted - «надрукувати за шаблоном».

`int(" 12 ")` сам прибирає пробіли по краях. Виняток у doctest записують так: рядок `Traceback (most recent call
last):`, потім `...` (усе середнє doctest пропускає) і останній рядок помилки дослівно.

## Типові помилки

| Що бачиш | Чому | Що робити |
|---|---|---|

> - `python3 -m flake8` - шукає помилки стилю і зайвий код, нічого не змінює. Назва: pyflakes + pep8: обʼєднав дві старі програми перевірки коду. `--max-line-length` - найбільша дозволена довжина рядка; викладач хоче 78 (типово 79).
> - `python3 -m pycodestyle` - перевіряє лише оформлення коду за PEP 8. Назва: Python code style - «стиль коду Python» (раніше програма звалась pep8). `--max-line-length` - найбільша довжина рядка; викладач хоче 78 (типово 79).
> - `python3 -m ruff check` - швидко шукає помилки в коді, з --fix сам виправляє. Назва: ruff - назва не розшифровується; check - «перевірити».
> - `python3 -m mypy` - перевіряє типи (int, str ...) без запуску програми. Назва: назва не розшифровується (py - від Python).
> - `grep` - знаходить рядки з текстом у файлах. Назва: g/re/p з редактора ed: «знайти регулярний вираз у всьому файлі і надрукувати». `-c` - лише порахувати рядки зі збігом у кожному файлі (count); `-n` - показати номер рядка перед кожним збігом (line number).

## Як роблять профі

- **TDD** (test-driven development) - «червоний → зелений → рефакторинг»: тест падає, мінімальний код, тест
  проходить, потім чистиш код. Заготовка з `NotImplementedError` - перший, «червоний» крок.
- **Граничні випадки - у тести першими**: порожній вхід, одна точка, однакові точки, нуль. Більшість помилок живе там.
- **Перевірка властивостей** (property-based testing, бібліотека Hypothesis): замість 5 прикладів - сотні випадкових,
  і перевіряється правило, напр. «S прямокутника = добуток сусідніх сторін».
- **Обчислення з матрицями і векторами** в науці роблять у NumPy (`numpy.cross`, `numpy.dot`, `A @ B`), але свої
  функції в ЛР7 - щоб розуміти формули.

Документація: `itertools.combinations` - https://docs.python.org/3/library/itertools.html#itertools.combinations ;
`NotImplementedError` - https://docs.python.org/3/library/exceptions.html#NotImplementedError

## Самоперевірка

1. Навіщо писати заготовку з `raise NotImplementedError` і тести до того, як пишеш код?
2. Що робить `del lst[2::3]` - вилучає числа 2, 5, 8 чи елементи на позиціях 2, 5, 8?
3. Як перевірити, що три точки простору лежать на одній прямій, без кутів і коренів?
4. Чому в режимі а) завдання 2 не можна перевіряти прямий кут через `== 0`, а в режимі б) можна?
5. Чому крайній елемент рядка може бути «особливим», хоча зліва (чи справа) від нього нічого нема?

<details markdown="1"><summary>Відповіді</summary>

1. Тести фіксують, що функція має робити, ще до коду; заготовка вже запускається, і видно, що саме не готове.
   Викладач прямо вимагає так (с. 3-4).
2. Елементи на позиціях 2, 5, 8 (з нуля) - зрізи працюють за позиціями, а не за значеннями.
3. Векторний добуток векторів AB і AC має бути нульовим вектором (с. 2) - лише множення і віднімання.
4. У режимі а) координати можуть бути дробовими, і float дає крихітну похибку; у режимі б) координати цілі, обчислення
   точні.
5. Умова «усі елементи зліва менші» для порожнього набору виконується (у Python `all()` порожнього - `True`); приклад
   с. 8 саме так і рахує `(1, 0)` і `(1, 2)`.
</details>
