Навіщо: програма майже ніколи не працює з першого разу. Цей урок вчить чотирьох простих способів знайти, де саме вона помиляється: прочитати traceback, надрукувати змінні, поставити assert і зупинити програму в breakpoint(). Усе в терміналі, без VS Code.

Коротко

Налагодження (debugging) - пошук місця, де програма робить не те, що ти думаєш. Помилка в програмі - баг.

Що бачиш З чого почати
Програма впала, у кінці Traceback ... і назва помилки прочитай traceback знизу вгору
Програма не падає, але число не те print(f"{x=}") або breakpoint()
Хочеш, щоб програма сама «кричала», коли дані погані assert умова, "повідомлення"
Програма впала, хочеш покопатись у змінних після падіння python3 -i файл.py

Traceback (слід виклику) - звіт Python про падіння. Читати знизу вгору:

Traceback (most recent call last):          ← «останній виклик - внизу»
  File ".../period.py", line 16, in <module>     ← звідки все почалось (рівень файлу)
    main()
  File ".../period.py", line 13, in main         ← потім функція main, рядок 13
    print(...)
  File ".../period.py", line 7, in period        ← тут упало: функція period, рядок 7
    return 2 * math.pi * math.sqrt(length / G)
                         ^^^^^^^^^^^^^^^^^^^^^   ← ^^^ показують, ЯКА саме частина рядка впала
ValueError: math domain error                    ← 1) ЧИТАЙ ПЕРШИМ: тип помилки і пояснення
  1. Останній рядок - що сталося (тип помилки + пояснення).
  2. Рядок над ним - де (файл, номер рядка, функція) і сам рядок коду з ^^^.
  3. Вище - як туди дійшли: хто кого викликав. Помилка не завжди в найнижчому рядку - часто погане значення прийшло згори (наприклад, від'ємна довжина в списку в main).

Python 3.12 підказує: Did you mean: '...'? (може, ти мав на увазі), Did you forget to import '...'? (забув імпорт), Perhaps you forgot a comma? (забув кому). Підказки корисні, але не завжди правильні (побачиш нижче).

Часті помилки в лабах першого курсу (справжній вивід Python 3.12.3)

SyntaxError і IndentationError не мають рядка Traceback (most recent call last): програма не запустилась зовсім, жоден рядок не виконався.

Друк для налагодження

Запис Що друкує
print(f"{x=}") x= і значення (рядки - в лапках!)
print(f"{x=:.3f}") те саме, 3 знаки після коми
print(f"{a / b = :.4f}") можна вираз; пробіли навколо = зберігаються
print(repr(s)) рядок «як є»: видно пробіли, \n, лапки
print(type(x)) тип: <class 'str'>, <class 'float'>
print(..., file=sys.stderr) друк у потік помилок, а не в звичайний вивід (потрібен import sys)

Перші команди pdb

breakpoint() у коді зупиняє програму і відкриває pdb (Python debugger, вбудований налагоджувач). Запрошення (Pdb) - він чекає команду.

Команда Від слова Що робить
p вираз print показати значення
n next виконати рядок і зупинитись на наступному (у функцію не заходить)
s step зробити крок всередину функції
c continue їхати далі до наступного breakpoint() або до кінця
l list показати код навколо; -> - рядок, який виконається наступним
q quit вийти (програма обривається)

Відповідь

'lengths', а не 'length' (справжній вивід - у кроці 1 «Руками»). Підказка рахує, яке ім'я «найближче» за буквами, і тут вгадала неправильно. Підказка - не наказ: дивись сам, що мав на увазі.

Відповідь

Крок 5. breakpoint() і перші кроки в pdb

Онови period.py до такого вигляду (assert лишається, у циклі додався breakpoint()):

import math

Типові помилки

  • Забутий налагоджувальний print у функції ламає doctest. doctest порівнює все, що функція надрукувала у звичайний вивід:

text Failed example: period(1.0) Expected: 'T = 2.006 с' Got: t=2.0060666807106475 'T = 2.006 с'

Друк з file=sys.stderr doctest не ловить (перевірено: той самий файл з print(f"{length=}", file=sys.stderr) показав length=1.0 на екрані, а в Got його нема). Але перед здачею прибери обидва. - Забутий breakpoint(). Програма «зависає» на (Pdb). А perevir (урок 03) замість цього пише doctest: файл питає input() при запуску. Дай відповіді після назви: perevir lab_bp.py 5, бо pdb теж читає з клавіатури. Нема input(), а таке повідомлення є - шукай breakpoint(): grep -n breakpoint *.py. - q у pdb дає traceback з bdb.BdbQuit. Це нормально, див. крок 5. - assert з дужками завжди «проходить». assert (length > 0, "текст") - це перевірка кортежу, а непорожній кортеж завжди істина. Python 3.12 попереджає: SyntaxWarning: assertion is always true, perhaps remove parentheses? і програма йде далі. Пиши без дужок: assert length > 0, "текст". - assert для перевірки вводу користувача. З python3 -O він зникає. Для вводу - звичайна умова й повідомлення (або виняток ValueError), assert - для «цього не може бути». - Читати лише перший рядок traceback. Головне - останній рядок і найнижчий рядок твого файлу. Рядки з /usr/lib/python3.12/... - це бібліотеки Python, їх зазвичай пропускаєш. - SyntaxError показує не той рядок. Для незакритої дужки Python 3.12 показує рядок, де дужку відкрито ('(' was never closed). Якщо повідомлення дивне - подивись і на рядок вище.

Як роблять профі

  • Python з кожною версією пояснює помилки краще: ^^^ під точним місцем з'явились у 3.11 (PEP 657), підказки Did you forget to import - у 3.12. Тому перше правило налагодження - уважно прочитати повідомлення.
  • print(f"{x=}") - нормальний інструмент і в 2026, але для програм довших за одну лабу професіонали переходять на logging (рівні DEBUG/INFO/WARNING, можна вимкнути одним рядком) - урок 06.
  • breakpoint() (PEP 553, Python 3.7+) замість старого import pdb; pdb.set_trace(): коротше і вимикається через PYTHONBREAKPOINT=0, а через PYTHONBREAKPOINT=ipdb.set_trace вмикає інший налагоджувач (урок 06). У Python 3.12 (Mint 22) pdb зупиняється на рядку після breakpoint() (у кроці 5 - рядок 15); з Python 3.13
  • одразу на рядку з breakpoint(). Також з 3.13 traceback кольоровий, а 3.14 вміє підключити pdb до вже запущеної програми: python -m pdb -p PID.
  • Лінтер ловить забуте: ruff (є у venv з уроку 03) має правила T100 (забутий breakpoint()) і T201 (забутий print): ruff check --select T100,T201 period.py (не в лабах - там print бувають потрібні).
  • У VS Code ті самі речі робить графічний налагоджувач (debugpy) - це урок 27, пізніше. pdb працює скрізь, де є термінал: на сервері, по ssh, на комп'ютері в аудиторії.

Самоперевірка

  1. Traceback має 3 рівні: <module> → main → period, останній рядок ValueError: math domain error. У якому рядку і якій функції програма впала? Чи обов'язково там помилка?
  2. Чим print(f"{x=}") кращий за print(x), коли x = "2"?
  3. Що зробить python3 -O файл.py з рядком assert g > 0, "g має бути додатне"?
  4. Ти в (Pdb) на рядку y = f(x). Чим відрізняються n і s? Що зробить c?
  5. Що надрукує python3 -i файл.py після падіння і чому там не видно локальних змінних функції?
Відповіді
  1. У функції period (найнижчий рівень, рядок з ^^^). Не обов'язково: там програма впала, а погане значення могло прийти згори, з main (як -1.5 у кроці 2).
  2. f"{x=}" друкує ім'я і repr значення: x='2'. Лапки показують, що це рядок, а print(x) надрукує просто 2.
  3. Нічого: -O вимикає всі assert, рядок не виконається.
  4. n виконає рядок повністю (разом з викликом f) і зупиниться на наступному; s зайде всередину f (--Call--). c поїде далі до наступного breakpoint() або до кінця програми.
  5. Traceback, а потім запрошення >>>, де доступні глобальні імена файлу (функції, константи). Локальні змінні функції живуть лише поки функція працює; після падіння їх уже нема. Їх показує import pdb; pdb.pm() (урок 06).
