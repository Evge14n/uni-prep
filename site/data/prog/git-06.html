Тема 6. gitignore для Python

Навіщо: у теці лаби, крім твого коду, Python сам наробить сміття: __pycache__/, .venv/ з тисячею файлів, картинки-графіки. Їм не місце в git: вони великі, у кожного свої і відтворюються запуском. .gitignore каже git їх не помічати.

Коротко

.gitignore - звичайний текстовий файл у корені репо (назва з крапкою на початку, тому ls без -a його не показує). Один рядок - один шаблон.

Рядок у .gitignore Що ігнорує
.venv/ теку віртуального середовища (сотні пакетних файлів)
__pycache__/ теку, куди Python кладе скомпільований код при import
*.pyc окремі такі файли (* - будь-які символи)
.pytest_cache/ кеш pytest
.mypy_cache/ кеш перевірки типів mypy
*.png усі картинки-результати (графіки з matplotlib)
!lr3/skhema.png ! - виняток: цей файл НЕ ігнорувати
# коментар коментар, лише з # на початку рядка

Нове тут:

  • * (asterisk) - будь-які символи в назві; bash сам замінює * на список файлів.
  • # (hash) - коментар: далі до кінця рядка bash не читає.

Як читати:

  • Слово з мінусом (як -v тут) - прапорець: уточнює, що саме зробити команді.
  • Якщо поруч у дужках стоїть довга назва з двома мінусами - це той самий прапорець, пиши будь-яку одну.
  • Символи ~ > * # набирай в англійській розкладці (~ - Shift і клавіша ліворуч від 1; # - Shift і 3 (в українській розкладці там №)).

Усе про кожну команду - у вкладці «Команди», а тут торкнись команди в коді - вискочить підказка.

Де стоїть / - вирішує, що і де ловить шаблон (git-scm.com/docs/gitignore):

  • / у кінці - лише тека (і все в ній): __pycache__/, .venv/.
  • / нема ніде, крім кінця - шаблон діє на будь-якій глибині: __pycache__/ спрацює і в lr1/, і в lr7/, *.pyc - теж.
  • / на початку або в середині - шлях рахується від теки, де лежить .gitignore: /dani/ - лише тека dani/ у корені (а lr1/dani/ - ні), lr3/skhema.png - лише цей файл (а lr5/lr3/skhema.png - ні).
Команда Що робить
git check-ignore -v файл який рядок якого .gitignore ігнорує файл
git rm --cached файл прибрати файл з git, але лишити на диску
git status --ignored показати і ігноровані файли теж

Нове тут:

  • git check-ignore - перевіряє, чи git пропускає файл і яке правило .gitignore винне. Назва: check ignore - «перевірити, чи ігнорується». -v (--verbose) - показати правило: файл .gitignore, номер рядка, шаблон і шлях (verbose - «докладно»).
  • git rm - видаляє файл з диска і git; --cached - лише з git. --cached - прибрати лише з git, файл на диску лишається (cached - «з кешу», стара назва індексу).
  • git status - показує, які файли змінено і що піде в наступний коміт (збережений знімок). --ignored - показати і файли, які приховує .gitignore (позначка !!) (ignored - «пропущені»).

Головне правило: .gitignore діє лише на файли, яких ще нема в git. Що вже закомічене - git і далі стежить, поки не скажеш git rm --cached.

Аналогія: .gitignore - список «не пакувати у валізу». Якщо светр уже у валізі, список його не викине - треба вийняти руками.

Пісочниця

На свіжій Mint 22.3 нема пакета python3-venv, і python3 -m venv падає з The virtual environment was not created successfully because ensurepip is not available. Якщо ти робив крок 0 уроку 03 курсу Linux Mint (Урок 03 - Термінал для лаб), пакет уже є. Якщо ні - один раз (попросить пароль):

Нове тут:

  • python3 - запускає Python: твій файл .py, один рядок коду або вбудований інструмент. Назва: Python - на честь комедійного шоу «Monty Python», 3 - третя версія мови. -m - запусти модуль Python (вбудований чи поставлений через pip) як програму, напр. python3 -m venv (module - «модуль»).
  • python3 -m venv - створює venv - окрему теку з Python і бібліотеками для лаб. Назва: virtual environment - «віртуальне середовище».
sudo apt install python3-venv

Нове тут:

  • sudo - виконує одну команду як адміністратор; спитає твій пароль (видно зірочки). Назва: superuser do - «зроби як суперкористувач» (адміністратор).
  • apt install - ставить програму з інтернету; на «Бажаєте продовжити? [Y/n]» - Enter. Назва: apt - Advanced Package Tool - «розширений інструмент для пакетів (програм)».

Тепер пісочниця:

mkdir ~/git-pisochnytsia-06
cd ~/git-pisochnytsia-06
git init
python3 -m venv .venv
printf 'def double(x):\n    return x * 2\n' > lr1.py
printf 'import lr1\nprint(lr1.double(4))\n' > main.py
python3 main.py
touch grafik.png
git status

Нове тут:

  • mkdir - створює нову теку. Назва: make directory - «зробити теку».
  • ~ (tilde) - твоя домашня тека, /home/evgen.
  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • git init - робить теку репозиторієм git (створює .git). Назва: init - від initialize, «почати, підготувати».
  • printf - друкує текст; \n у ньому - Enter (новий рядок). Назва: print formatted - «надрукувати за шаблоном».
  • '...' (single quotes) - текст буквально: $, * і пробіли всередині - звичайні символи.
  • > (redirect) - пише вивід у файл, старий вміст стирає.
  • touch - створює порожній файл; якщо файл уже є - вміст не чіпає. Назва: touch - «торкнутися» файлу.

python3 main.py надрукує 8, а заодно створить __pycache__/lr1.cpython-312.pyc (бо main.py імпортує lr1). touch grafik.png - уяви, що це графік, який зберіг matplotlib.

У .venv/ понад тисячу файлів (у перевірці git нарахував 1014). git add . зараз потягнув би їх усі.

Нове тут:

  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт). . - усе в поточній теці і підтеках; спершу глянь git status, щоб не додати зайве.

Передбач, потім запусти

Створи .gitignore (у nano впиши 5 рядків, Ctrl+O, Enter, Ctrl+X) або одним рядком через printf:

nano .gitignore
# або те саме без nano, одним рядком:
printf '.venv/\n__pycache__/\n*.pyc\n.pytest_cache/\n.mypy_cache/\n' > .gitignore

Нове тут:

  • nano - простий редактор файлів у терміналі. Назва: nano - жарт з одиницями: наступник редактора pico (піко < нано).
  1. git status --short - які файли лишаться в списку?
Відповідь

Нове тут:

  • git status: --short - коротко: по рядку на файл з двома буквами стану (M, A, ??) (short - «коротко»).

.venv/ і __pycache__/ зникли, а сам .gitignore зʼявився - його теж треба комітити. grafik.png ще видно: правила для *.png поки нема.

?? .gitignore
?? grafik.png
?? lr1.py
?? main.py
  1. git check-ignore -v __pycache__/lr1.cpython-312.pyc - який рядок спрацює: __pycache__/ чи *.pyc?
Відповідь

Рядок 2, __pycache__/: git ігнорує всю теку і всередину вже не дивиться. Формат: файл:номер рядка:шаблон, потім Tab і шлях.

.gitignore:2:__pycache__/   __pycache__/lr1.cpython-312.pyc
  1. git check-ignore -v main.py - що виведе?
Відповідь

Нічого, і код виходу 1 (echo $? покаже 1): main.py не ігнорується. Тиша тут - добра новина.

Нове тут:

  • echo - друкує на екран текст, який йому дали. Назва: echo - «луна»: повторює те, що йому дали.

Руками

Крок 1. Комітимо разом з графіком (наче ти ще не знав про *.png):

git add .
git commit -m "ЛР1 і gitignore"

[main (root-commit) bf8917a] ЛР1 і gitignore
 4 files changed, 9 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 grafik.png
 create mode 100644 lr1.py
 create mode 100644 main.py

Нове тут:

  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати». -m (--message) - повідомлення коміту одразу в команді; без -m відкриється nano (message - «повідомлення»).
  • "..." (double quotes) - усе між лапками - одне слово, навіть з пробілами.

4 файли: .venv/ і __pycache__/ у коміт не пішли. (Хеш у тебе буде інший.)

Крок 2. Пізно додали правило. Дописуємо *.png і «перемальовуємо» графік:

printf '*.png\n' >> .gitignore
printf 'новий графік\n' > grafik.png
git status --short
git check-ignore -v grafik.png

 M .gitignore
 M grafik.png

Нове тут:

  • >> (append) - дописує вивід у кінець файлу.

grafik.png досі в списку змінених, а check-ignore мовчить: файл уже в git, і правило на нього не діє.

Крок 3. Прибрати з git, лишити на диску.

git rm --cached grafik.png
git status --short

rm 'grafik.png'

 M .gitignore
D  grafik.png

D у першій колонці - «видалення з репо підготовлене до коміту». Файл на диску не чіпали.

git add .gitignore
git commit -m "Не зберігай картинки-результати"
ls grafik.png
git status --short

[main d84d1e0] Не зберігай картинки-результати
 2 files changed, 1 insertion(+)
 delete mode 100644 grafik.png

Нове тут:

  • ls - показує, що лежить у теці. Назва: list - «список» (вмісту теки).
grafik.png

ls grafik.png показав файл - він на диску (якби його не було, ls написав би No such file or directory). git status --short порожній - тепер git його справді ігнорує. Перевір: git check-ignore -v grafik.png → .gitignore:6:*.png grafik.png.

Для лаб: один .gitignore у корені ~/univer/labs діє на всі теки lr1 ... lr7. Візьми ті самі 6 рядків (.venv/, __pycache__/, *.pyc, .pytest_cache/, .mypy_cache/, *.png). Якщо до звіту ЛР3 треба саме цю схему - допиши виняток !lr3/skhema.png. Зроби .gitignore до першого git add ., тоді git rm --cached не знадобиться.

Типові помилки

  • Додаєш ігнорований файл руками: text The following paths are ignored by one of your .gitignore files: grafik.png hint: Use -f if you really want to add them. hint: Turn this message off by running hint: "git config advice.addIgnoredFile false" git питає «ти впевнений?». Якщо файл справді треба - git add -f grafik.png, але краще виняток ! у .gitignore.
  • Правило написане, а файл досі в git status як змінений (M) - він закомічений раніше. Лікування - git rm --cached файл і коміт (крок 3).
  • Закомітив цілу .venv/ (у перевірці це 1014 файлів в одному коміті). Прибрати з git, не чіпаючи середовище (-r - рекурсивно, -q - тихо, без тисячі рядків rm '...'): bash git rm -r -q --cached .venv git commit -m "Прибери .venv з репо"

Нове тут:

  • git rm: -r - цілу теку з усім, що всередині (recursive - «рекурсивно»: і в усіх підтеках); -q (--quiet) - не друкувати рядок rm '...' на кожен файл (quiet - «тихо»).

Не забудь .venv/ у .gitignore, інакше наступний git add . поверне її. - Коментар у тому ж рядку: *.png # картинки не працює - git шукає файл, що закінчується на .png # картинки. git status --short і далі показує ?? a.png. Коментар - лише окремим рядком з # на початку. - Файл назвали gitignore (без крапки) або .gitignore.txt - git його не читає. Перевір ls -a: має бути рівно .gitignore.

Нове тут:

  • ls: -a (--all) - показати й приховані (назва з крапки), разом з . і .. (all - «усі»).

Як роблять профі

  • Не пишуть з нуля, а беруть шаблон GitHub Python.gitignore (репо github/gitignore; 18.11.2026 у ньому 223 рядки, є __pycache__/, *.py[codz], .pytest_cache/, .venv, .mypy_cache/). Його ж підставляє сайт при створенні репо (поле «Add .gitignore» → Python) і gh. Це для нового проєкту, не для пісочниці: wget -O .gitignore перезапише твій .gitignore, а gh repo create створить на GitHub ще один репо (і потребує входу в gh, урок 16). Тому тут лише зразок, НАЗВА - твоя назва нового репо: text wget -O .gitignore https://raw.githubusercontent.com/github/gitignore/main/Python.gitignore gh repo create НАЗВА --private --gitignore Python Прочитай шаблон перед комітом: там є, наприклад, lib/ і build/ - тека lib/ з твоїм кодом теж стане ігнорованою.
  • Особисте сміття твого редактора (*.swp, *~) пишуть не в .gitignore проєкту, а в глобальний файл ~/.config/git/ignore - він діє в усіх репо на твоєму компʼютері (git-scm.com/docs/gitignore: якщо core.excludesFile не задано, береться $HOME/.config/git/ignore): bash mkdir -p ~/.config/git printf '*.swp\n' > ~/.config/git/ignore touch .lr1.py.swp git check-ignore -v .lr1.py.swp text /home/.../.config/git/ignore:1:*.swp .lr1.py.swp

Нове тут:

  • mkdir: -p (--parents) - створює й усі проміжні теки шляху; тека вже є - без помилки (parents - «батьківські»).

(замість ... - твоя домашня тека.) - git check-ignore -v --no-index файл - показує правило навіть для вже закоміченого файлу (без --no-index git про такі мовчить, як у кроці 2). - git status --ignored - глянути, що саме зараз ігнорується (чи не сховав ти щось потрібне). - Python 3.13+ сам кладе в нову .venv/ файл .gitignore з * (docs.python.org, venv: «Changed in version 3.13: venv now creates a .gitignore file for Git by default»). На Mint 22 Python 3.12 - тому .venv/ у свій .gitignore пишемо самі.

Нове тут:

  • git check-ignore: --no-index - перевіряти й файли, які вже в git (без нього вони завжди «не ігноровані»).

Самоперевірка

  1. Що буде з grafik.png, якщо він уже закомічений, а ти дописав *.png у .gitignore?
  2. Чим git rm --cached lr1.png відрізняється від rm lr1.png?
  3. Яка команда скаже, через який рядок .gitignore ігнорується файл?
  4. Чому *.png # графіки в .gitignore не ігнорує grafik.png?
  5. Що з цього писати в .gitignore проєкту, а що в ~/.config/git/ignore: __pycache__/, *.swp від твого редактора?

Нове тут:

  • rm - видаляє файли назавжди, без кошика. Назва: remove - «прибрати, видалити».
Відповіді
  1. Нічого: git і далі стежить за ним (M grafik.png у статусі). Треба git rm --cached grafik.png і коміт.
  2. git rm --cached прибирає файл лише з git, на диску він лишається; rm видаляє з диска.
  3. git check-ignore -v файл (для вже закоміченого - з --no-index).
  4. Коментар можна лише окремим рядком; тут # графіки стало частиною шаблону.
  5. __pycache__/ - у .gitignore проєкту (стосується всіх, хто працює з кодом); *.swp - у глобальний, це звичка лише твого редактора.
