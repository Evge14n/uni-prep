Тема 7. Гілки - branch, switch, merge

Навіщо: ЛР1 здана і працює, а ЛР2 ти лише почав і вона поки ламається. Гілка дає робити ЛР2 окремо: main лишається робочою, а коли ЛР2 готова - зливаєш її в main однією командою.

Коротко

Гілка - це просто назва-ярлик, приклеєний до одного коміту. Новий коміт пересуває ярлик поточної гілки вперед. HEAD - «де я зараз»: на якій гілці стою. Копій файлів гілка не робить, тому вона створюється миттєво.

Команда Що робить
git branch список гілок, * - поточна
git switch -c lr2 створити гілку lr2 і перейти на неї
git switch main перейти на main (файли в теці стануть як у main)
git merge lr2 злити lr2 у поточну гілку
git branch -d lr2 видалити гілку (лише якщо вже злита)
git log --oneline --graph --all малюнок усіх гілок

Нове тут:

  • git branch - показує, створює і видаляє гілки (окремі лінії змін проєкту). -d (--delete) - видалити гілку, якщо її коміти вже злито (додано в іншу гілку); інакше відмовить (delete - «видалити»).
  • git switch - перемикає на іншу гілку (лінію змін); з -c створює нову. -c (--create) - створити нову гілку від поточного місця і перейти на неї (create - «створити»).
  • git merge - додає зміни іншої гілки в ту, де ти зараз.
  • git log - показує історію комітів, новий зверху. --oneline - по рядку на коміт: 7 знаків хешу і перший рядок повідомлення; --graph - малює гілки зліва зірочками і лініями; --all - коміти всіх гілок, а не лише поточної.
  • * (asterisk) - будь-які символи в назві; bash сам замінює * на список файлів.

Як читати:

  • Слово з мінусом (як -c тут) - прапорець: уточнює, що саме зробити команді.
  • Якщо поруч у дужках стоїть довга назва з двома мінусами - це той самий прапорець, пиши будь-яку одну.
  • Символи ~ > * # набирай в англійській розкладці (~ - Shift і клавіша ліворуч від 1; # - Shift і 3 (в українській розкладці там №)).

Усе про кожну команду - у вкладці «Команди», а тут торкнись команди в коді - вискочить підказка.

Два види злиття:

1) Fast-forward (перемотування): main не рухався, поки ти робив lr2
   до:     A ← B          після:  A ← B
           ↑   ↑                      ↑
         main  lr2                main, lr2
   Нового коміту нема: ярлик main просто пересунули вперед.

2) Merge-коміт: обидві гілки пішли вперед
   до:                          після:
   A ← B ← D     (main)         A ← B ← D ← M   (main)
        \                            \     /
         C       (lr3)                C ──      (lr3)
   git робить новий коміт M з ДВОМА батьками (D і C).

Аналогія: main - чистовик, гілка - чернетка. Fast-forward - коли чистовик не чіпали і чернетку просто оголосили чистовиком. Merge-коміт - коли в чистовику теж щось дописали, і треба звести обидва в одне.

Старі підручники пишуть git checkout -b lr2 і git checkout main - це те саме, що git switch -c lr2 і git switch main (switch є з git 2.23, він простіший і робить лише одне).

Нове тут:

  • git checkout - стара команда: перемикає гілку або стирає зміни у файлі. Назва: check out - «взяти» (як книжку в бібліотеці). -b - створити нову гілку і перейти на неї, як git switch -c (branch - «гілка»).

Пісочниця

mkdir ~/git-pisochnytsia-07
cd ~/git-pisochnytsia-07
git init
printf 'def double(x):\n    return x * 2\n' > lr1.py
git add lr1.py
git commit -m "ЛР1 готова"
git branch

* main

Нове тут:

  • mkdir - створює нову теку. Назва: make directory - «зробити теку».
  • ~ (tilde) - твоя домашня тека, /home/evgen.
  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • git init - робить теку репозиторієм git (створює .git). Назва: init - від initialize, «почати, підготувати».
  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт).
  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати». -m (--message) - повідомлення коміту одразу в команді; без -m відкриється nano (message - «повідомлення»).
  • printf - друкує текст; \n у ньому - Enter (новий рядок). Назва: print formatted - «надрукувати за шаблоном».
  • '...' (single quotes) - текст буквально: $, * і пробіли всередині - звичайні символи.
  • > (redirect) - пише вивід у файл, старий вміст стирає.
  • "..." (double quotes) - усе між лапками - одне слово, навіть з пробілами.

Передбач, потім запусти

  1. Створюємо гілку, комітимо в ній новий файл і повертаємось на main. Що покаже ls?
git switch -c lr2
printf 'print("ЛР2")\n' > lr2.py
git add lr2.py
git commit -m "ЛР2: початок"
git switch main
ls

Нове тут:

  • ls - показує, що лежить у теці. Назва: list - «список» (вмісту теки).
Відповідь 
lr1.py

lr2.py зник з теки - але не з git: він у коміті гілки lr2. git switch переписує файли в теці під вибрану гілку. Повернешся на lr2 - файл зʼявиться.

  1. git merge lr2 (зараз ти на main) - буде новий коміт чи ні? Запустиш у кроці 2.
Відповідь

Ні, це fast-forward: main не мінявся, поки ти робив lr2, тож git просто пересуває ярлик main вперед. Слово Fast-forward буде прямо у виводі.

  1. Тепер гілка lr3 з одним комітом, а в main тим часом коміт з README. Що буде при git merge lr3?
Відповідь

Нове тут:

  • git merge: lr3 - яку гілку злити В ПОТОЧНУ: спершу git switch main, потім git merge lr3.

Merge-коміт: обидві гілки пішли вперед, перемотати не вийде. Деталі - у кроці 3 нижче.

Руками

Крок 1. Подивись на гілки до злиття. Ти на main:

git log --oneline --graph --all

* 0879f44 (lr2) ЛР2: початок
* c03fdc0 (HEAD -> main) ЛР1 готова

У дужках - ярлики. HEAD -> main значить «я на гілці main», а lr2 на коміт попереду. Хеші в тебе будуть інші - дивись на будову.

Крок 2. Fast-forward і прибирання.

git merge lr2
git branch -d lr2

Updating c03fdc0..0879f44
Fast-forward
 lr2.py | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 lr2.py

Deleted branch lr2 (was 0879f44).

Коміти ЛР2 нікуди не ділись: вони тепер у main. Видалили лише ярлик.

Крок 3. Merge-коміт.

git switch -c lr3
printf 'print("ЛР3")\n' > lr3.py
git add lr3.py
git commit -m "ЛР3: початок"
git switch main
printf '# Лаби\n' > README.md
git add README.md
git commit -m "Додай README"
git log --oneline --graph --all

* c3d4a00 (HEAD -> main) Додай README
| * 5fe4c9d (lr3) ЛР3: початок
|/
* 0879f44 ЛР2: початок
* c03fdc0 ЛР1 готова

Гілки розійшлись від 0879f44. Зливаємо:

git merge lr3

На Mint тут відкриється nano з готовим повідомленням Merge branch 'lr3'. Нічого не міняй: Ctrl+O, Enter, Ctrl+X.

Merge made by the 'ort' strategy.
 lr3.py | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 lr3.py

ort - назва алгоритму злиття за замовчуванням, на нього можна не зважати.

git log --oneline --graph --all
git log -n 1

*   be97404 (HEAD -> main) Merge branch 'lr3'
|\
| * 5fe4c9d (lr3) ЛР3: початок
* | c3d4a00 Додай README
|/
* 0879f44 ЛР2: початок
* c03fdc0 ЛР1 готова

Нове тут:

  • git log: -n (--max-count) - лише N останніх комітів: -n 3 (або коротко -3) (number - «число»).
commit be9740421acfc7c43e1bb2c9603d61f28df43354 (HEAD -> main)
Merge: c3d4a00 5fe4c9d
Author: Твоє Імʼя <128326252+Evge14n@users.noreply.github.com>

Рядок Merge: c3d4a00 5fe4c9d - два батьки. На малюнку дві лінії сходяться в одну. Тепер git branch -d lr3 → Deleted branch lr3 (was 5fe4c9d).

Для лаб: у ~/univer/labs тримай main таким, щоб усі здані лаби працювали. Нову лабу починай гілкою: git switch -c lr4, комітиш крок за кроком, а коли doctest проходить - git switch main, git merge lr4, git branch -d lr4. Якщо посеред ЛР4 викладач просить виправити ЛР3 - git switch main, правиш, комітиш, і назад git switch lr4.

Типові помилки

  • Гілки з такою назвою нема (git switch lr9), код виходу 128: text fatal: invalid reference: lr9 Глянь git branch. Створити нову - git switch -c lr9.
  • Гілка вже є (git switch -c main): text fatal: a branch named 'main' already exists Перейти на неї - без -c: git switch main.
  • Видаляєш гілку, яку ще не злив (git branch -d lr4): text error: the branch 'lr4' is not fully merged. If you are sure you want to delete it, run 'git branch -D lr4' Це запобіжник: її коміти ніде більше нема. Спершу git merge lr4. Велика -D видаляє силою - коміти гілки загубляться (рятувати їх - урок 12, reflog).
  • Перемикаєшся, а в теці незакомічені зміни файлу, який у тій гілці інший: text error: Your local changes to the following files would be overwritten by checkout: lr1.py Please commit your changes or stash them before you switch branches. Aborting git нічого не зробив і лишив тебе на місці. Закоміть зміни (або відклади - урок 13, stash), потім перемикайся.
  • Незакомічені зміни їдуть з тобою в іншу гілку, якщо не заважають: git switch lr4 пише text M README.md Switched to branch 'lr4' M README.md - твоя правка з main тепер у теці на lr4. Зміна належить гілці лише після коміту. Правило: перед git switch - git status чистий.

Як роблять профі

  • Гілка живе недовго: одна задача (одна лаба, одна правка) - одна гілка, злили - видалили. Так працює GitHub flow (docs.github.com, «GitHub flow»): main завжди робочий, зміни - через гілки і Pull Request (урок 11).
  • git switch - - назад на попередню гілку (як cd -): bash git switch -

Нове тут:

  • git switch: - - назад на попередню гілку (як cd -).
  • Швидкий огляд гілок і того, що вже злито (те, що в --merged, можна сміливо -d): bash git branch -v git branch --merged ```text lr4 d7d4232 ЛР4: змінна x
  • main be97404 Merge branch 'lr3' ```

Нове тут:

  • git branch: -v (--verbose) - біля гілки - її останній коміт; -vv - ще й повʼязана гілка на GitHub (verbose - «докладно»); --merged - лише гілки, чиї коміти вже є в поточній - їх можна сміливо -d (merged - «злиті»).

text * main lr4 нема в --merged - її ще не злито. - Деякі команди просять завжди merge-коміт, навіть коли можна перемотати, щоб в історії було видно «тут злили гілку»: git merge --no-ff lr5. Інші, навпаки, тримають історію прямою (rebase, squash - див. урок 11, види merge на GitHub). - Назви гілок короткі, латиницею, без пробілів: lr4, lr3-vypravlennia, fix-doctest.

Самоперевірка

  1. Що таке гілка в git і чому вона створюється миттєво?
  2. Коли git merge робить fast-forward, а коли - merge-коміт?
  3. Ти на main, а lr2.py є лише в гілці lr2. Чому ls його не показує і як його побачити?
  4. git branch -d lr4 пише not fully merged. Що це значить і що зробиш?
  5. Яка команда малює всі гілки з ярликами HEAD -> main?
Відповіді
  1. Ярлик (назва), що вказує на один коміт. Файли не копіюються - тому миттєво.
  2. Fast-forward - коли поточна гілка не мінялась після відгалуження (просто пересунути ярлик). Merge-коміт - коли обидві гілки мають нові коміти.
  3. git switch ставить у теку файли поточної гілки. git switch lr2 - і lr2.py зʼявиться.
  4. У lr4 є коміти, яких нема в main. Спершу git merge lr4 (з main), потім -d. -D - лише якщо ці коміти справді не потрібні.
  5. git log --oneline --graph --all.
