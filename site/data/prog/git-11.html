Тема 11. Pull Request - гілка, рев'ю, merge

Навіщо: ЛР3 робиш у гілці lr3, а в main вона потрапляє через Pull Request. Так видно всі зміни лаби одним списком, одногрупник або викладач може залишити коментар до рядка, а main лишається робочою.

Коротко

Pull Request (PR) - прохання на GitHub: «злий мою гілку lr3 у main». У PR є опис, список комітів, усі зміни (вкладка Files changed) і коментарі. Номер PR іде в тому ж рахунку, що й issues: якщо в репо вже є issue #1, перший PR буде #2 (у docs дослівно не знайшов - не перевірено).

Рев'ю (review) - перевірка чужого коду. Рецензент обирає одне з трьох: - Comment - просто коментар; - Approve - «можна зливати»; - Request changes - «спершу виправ».

Автор PR не може схвалити (Approve) свій власний PR - так прямо пише документація GitHub. Тож зі свого акаунта у своєму PR лишається Comment. Approve дає лише інша людина, наприклад одногрупник з доступом до репо. Request changes - теж його кнопка (чи дає GitHub її автору, документація не каже - не перевірено).

main:  A ─────────────── M        ← після злиття
        \               /
lr3:     B ── C ── (PR #2, рев'ю)
Крок Команда або кнопка
гілка під лабу git switch -c lr3
коміти git add, git commit
гілку на GitHub git push -u origin lr3
відкрити PR жовта плашка Compare & pull request або gh pr create
рев'ю Files changed → коментар до рядка → Review changes
злити Merge pull request (або Squash / Rebase)
прибрати за собою git switch main, git pull, git branch -d lr3, видалити гілку на GitHub

Три види злиття на GitHub (кнопка Merge з випадним списком):

Кнопка Що зʼявиться в main Як те саме в git
Create a merge commit усі коміти гілки + окремий коміт злиття з двома батьками git merge --no-ff
Squash and merge один новий коміт «Назва PR (#2)», коміти гілки в main не потрапляють git merge --squash + git commit
Rebase and merge коміти гілки по одному, без коміту злиття, але з новими хешами rebase + fast-forward

Аналогія: PR - як здати чернетку лаби на перевірку. Викладач пише зауваження на полях (коментарі до рядків), ставить «зараховано» (Approve) або «переробити» (Request changes), і лише потім робота йде в чистовик (main).

Передбач, потім запусти

  1. main не рухалась, тож git merge lr3 зробив би fast-forward (урок 07). А що зробить git merge --no-ff lr3?
Відповідь

Створить коміт злиття навіть там, де можна було просто пересунути вказівник. Саме так зливає кнопка «Create a merge commit»:

*   2f51e50 (HEAD -> proba-merge) Merge pull request #2 from Evge14n/lr3
|\  
| * c4894c4 (origin/lr3, lr3) ЛР3: завдання 2
| * 3204bab ЛР3: заготовка
|/  
* d850e97 (origin/main, origin/HEAD, main) Initial commit

У дужках - ярлики гілок: ти на proba-merge (HEAD ->), lr3 і її копія на GitHub origin/lr3 стоять на «завдання 2», а main - ще на «Initial commit».

  1. git merge --squash lr3 - чи буде одразу новий коміт?
Відповідь

Ні. Git лише складе всі зміни гілки в індекс і скаже Squash commit -- not updating HEAD. git status --short покаже A lr3.py. Коміт робиш сам: git commit -m "ЛР3 (#2)". В історії - один коміт замість двох:

* 623fcfe (HEAD -> proba-squash) ЛР3 (#2)
* d850e97 (origin/main, origin/HEAD, main) Initial commit
  1. На GitHub гілку lr3 після злиття видалили. Що покаже git branch -r у другому клоні, де не було fetch?
Відповідь

Досі origin/lr3. Git не знає про видалення, поки не спитає GitHub. Прибирає її git fetch --prune:

From github.com:Evge14n/pisochnytsia
 - [deleted]         (none)     -> origin/lr3

Руками

Пісочниця ~/pisochnytsia. Хеші в тебе будуть інші.

Крок 1. Гілка з двома комітами і push.

cd ~/pisochnytsia
git switch main
git pull
git switch -c lr3
printf 'x = 3\nprint("ЛР3:", x)\n' > lr3.py
git add lr3.py
git commit -m "ЛР3: заготовка"
printf 'print("ЛР3: завдання 2")\n' >> lr3.py
git commit -am "ЛР3: завдання 2"
git push -u origin lr3

To github.com:Evge14n/pisochnytsia.git
 * [new branch]      lr3 -> lr3
branch 'lr3' set up to track 'origin/lr3'.

Нове тут:

  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • git switch - перемикає на іншу гілку (-c - створює нову). Назва: switch - «перемкнути». -c - створити нову гілку від поточного місця і перейти на неї.
  • git pull - забирає нові коміти з GitHub і зливає у твою гілку. Назва: pull - «потягнути»: забрати нові коміти з GitHub до себе.
  • printf - друкує текст за шаблоном; \n - Enter. Назва: print formatted - «надрукувати за шаблоном».
  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт).
  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати»: зберегти знімок змін в історію. -m - повідомлення коміту одразу в команді; без -m відкриється nano; -a - спершу сам додає зміни ВЖЕ відстежуваних файлів; нові файли - ні.
  • git push - відправляє твої коміти на GitHub. Назва: push - «штовхнути»: відправити свої коміти на GitHub. -u - запамʼятати звʼязок гілки з GitHub; далі просто git push і git pull.
  • ~ - домашня тека /home/evgen. Назва: tilde («тильда») - домашня тека.
  • "..." - текст з пробілами одним словом, $ підставляється. Назва: подвійні лапки - «усе це одне слово, але $ працює».
  • '...' - текст буквально, нічого не підставляється. Назва: одинарні лапки - «буквально, як написано».
  • > - пише вивід у файл, старий вміст стирає. Назва: redirect - «перенаправлення» виводу у файл.
  • >> - дописує вивід у кінець файлу. Назва: append - «дописати» в кінець файлу.

Усе про кожну команду - у вкладці «Команди», а тут торкнись команди в коді - вискочить підказка.

Крок 2. Відкрити PR на сайті.

github.com/Evge14n/pisochnytsia → жовта плашка над списком файлів → Compare & pull request
base: main  ←  compare: lr3
Title: ЛР3
опис: Заготовка і завдання 2
Create pull request

Або з терміналу:

gh pr create --base main --head lr3 --title "ЛР3" --body "Заготовка і завдання 2"
gh pr list

Нове тут:

  • gh pr create - створює Pull Request з поточної гілки. Назва: pr - pull request, «запит на злиття» гілки в main; create - «створити». --base - куди зливати: --base main; --head - яку гілку зливати; без нього - поточна; --title - назва PR; --body - опис PR; рядок Closes #1 закриє Issue №1 при злитті.
  • gh pr list - показує список Pull Requests репо. Назва: pr - pull request, «запит на злиття»; list - «список».

Крок 3. Рев'ю. Відкрий PR → вкладка Files changed. Наведи мишку на рядок x = 3 → синя іконка коментаря → напиши «краще назвати змінну n?» → Start a review. Потім угорі Review changes → вибери Comment / Approve / Request changes → Submit review. Зі свого акаунта у своєму PR вибирай Comment: Approve власного PR GitHub не дає, а Approve і Request changes - кнопки одногрупника.

Те, що рецензент бачить у Files changed, можна побачити і в терміналі. Другий клон (як в уроці 09; якщо його нема - git clone git@github.com:Evge14n/pisochnytsia.git ~/druhyi-klon):

cd ~/druhyi-klon
git fetch
git diff --stat origin/main...origin/lr3
git diff origin/main...origin/lr3

 lr3.py | 3 +++
 1 file changed, 3 insertions(+)
diff --git a/lr3.py b/lr3.py
new file mode 100644
index 0000000..549455e
--- /dev/null
+++ b/lr3.py
@@ -0,0 +1,3 @@
+x = 3
+print("ЛР3:", x)
+print("ЛР3: завдання 2")

Нове тут:

  • git fetch - забирає новини з GitHub, нічого не зливаючи. Назва: fetch - «принести, забрати».
  • git diff - показує, які рядки змінено (+ додано, - прибрано). Назва: diff - від difference, «різниця». --stat - замість рядків - підсумок: які файли і скільки рядків змінено; origin/main...origin/lr3 - три крапки: що змінилось у lr3 від місця, де вона відгалузилась від main (як Files changed у PR). Три крапки main...lr3 = «що змінилось у lr3 від місця, де вона відгалузилась від main». Рецензія з gh. Коментар можеш лишити і ти сам:
gh pr review 2 --comment -b "Глянь назву змінної x"

Нове тут:

  • gh pr review - лишає рецензію на PR: коментар, схвалення чи «переробити». Назва: pr - pull request; review - «перевірка, рецензія». --comment - просто коментар (зі свого акаунта у своєму PR - лише так); -b - текст рецензії: -b "Глянь назву змінної x"; 2 - номер PR. А ці дві команди - для одногрупника у його терміналі, з його акаунта (у тебе як автора --approve не пройде):
gh pr review 2 --approve
gh pr review 2 --request-changes -b "Додай doctest"

Крок 4. Як виглядатиме історія - модель у git. Кнопку на сайті в перевірці не натиснеш, тож змоделюємо два види злиття локально, у пробних гілках:

cd ~/pisochnytsia
git switch -c proba-merge main
git merge --no-ff lr3 -m "Merge pull request #2 from Evge14n/lr3"
git log --oneline --graph -4
git switch -c proba-squash main
git merge --squash lr3
git commit -m "ЛР3 (#2)"
git log --oneline --graph -3
git switch main
git branch -D proba-merge proba-squash

Нове тут:

  • git merge - зливає іншу гілку в поточну. Назва: merge - «злити, обʼєднати». --no-ff - завжди робити окремий коміт злиття, навіть якщо можна просто «перемотати» (як кнопка Merge на GitHub); -m - повідомлення коміту злиття; без нього git відкриє nano; lr3 - яку гілку злити В ПОТОЧНУ: спершу git switch main, потім git merge lr3; --squash - усі зміни гілки одним шматком в індекс, без коміту; далі git commit (як Squash and merge).
  • git log - показує історію комітів, новий зверху. Назва: log - «журнал»: історія комітів. --oneline - по рядку на коміт: 7 знаків хешу і перший рядок повідомлення; --graph - малює гілки зліва зірочками і лініями.
  • git branch - показує, створює і видаляє гілки. Назва: branch - «гілка». -D - видалити гілку навіть незлиту (= --delete --force); її коміти зникнуть з видимості. Виводи log - у пунктах 1 і 2 «Передбач». -D (велике) видаляє гілку навіть незлиту - тут можна, це пробні гілки. Повідомлення як на GitHub: merge-коміт - «Merge pull request #2 from Evge14n/lr3» і назва PR другим абзацом; squash - «ЛР3 (#2)» (так виглядають коміти в репо cli/cli і facebook/react, глянув 18.11.2026).

Крок 5. Злити на сайті і прибрати. У PR унизу Merge pull request → Confirm merge → зʼявиться кнопка Delete branch - натисни. Потім у терміналі:

git switch main
git pull
git log --oneline --graph -4
git branch -d lr3
git fetch --prune
git branch -a

Нове тут:

  • git branch: -d - видалити гілку, якщо її коміти вже злито; інакше відмовить; -a - і твої, і віддалені гілки (remotes/origin/...).
  • git fetch: --prune - прибрати в себе origin/ГІЛКА, яких на GitHub уже нема (видалили після PR). git log покаже (пробіли в кінці рядків графа не важать):
*   0b4e2f1 (HEAD -> main, origin/main, origin/HEAD) Merge pull request #2 from Evge14n/lr3
|\  
| * c4894c4 (origin/lr3, lr3) ЛР3: завдання 2
| * 3204bab ЛР3: заготовка
|/  
* d850e97 Initial commit

Зверни увагу: origin/lr3 ще є, хоч на сайті гілку видалено. git pull віддалені гілки не прибирає - це робить git fetch --prune. Далі:

Deleted branch lr3 (was c4894c4).
From github.com:Evge14n/pisochnytsia
 - [deleted]         (none)     -> origin/lr3
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/main

Якщо на сайті не натиснув Delete branch - видали віддалену гілку з терміналу:

git push origin --delete lr3

To github.com:Evge14n/pisochnytsia.git
 - [deleted]         lr3

Нове тут:

  • git push: --delete - видалити гілку або тег на GitHub: git push origin --delete lr3.

Типові помилки

1. Після Squash and merge git branch -d lr3 то відмовляє, то видаляє. У main на GitHub зʼявився новий squash-коміт, а самих комітів lr3 там нема. -d видаляє лише злиту гілку, і «злита» він перевіряє так: якщо в тебе є origin/lr3 - чи все з lr3 є в origin/lr3; якщо origin/lr3 нема - чи все є в поточній гілці (main). Тому буває два випадки (обидва перевірено, git 2.43):

  • origin/lr3 уже нема: на сайті натиснув Delete branch і потім зробив git fetch --prune (або сам видалив гілку git push origin --delete lr3). Тоді -d відмовляє, код виходу 1:
error: the branch 'lr3' is not fully merged.
If you are sure you want to delete it, run 'git branch -D lr3'
  • origin/lr3 ще є: гілку на сайті не видаляв, або видалив, але ще не робив git fetch --prune (звичайний git pull віддалені гілки не прибирає). Тоді -d бачить, що все з lr3 лежить в origin/lr3, пише попередження і видаляє, код 0:
warning: deleting branch 'lr3' that has been merged to
         'refs/remotes/origin/lr3', but not yet merged to HEAD
Deleted branch lr3 (was 6214452).

Попередження чесне: «злита в origin/lr3, але не в HEAD». Тобто git перевірив лише, що лаба запушена, а не що вона в main.

Якщо -d відмовив, а PR на сайті справді злитий (на сторінці PR позначка Merged, не перевірено) - видаляй силою:

git branch -D lr3

2. «Your branch is up to date», а на GitHub уже злитий PR. Після злиття на сайті git switch main пише:

Your branch is up to date with 'origin/main'.

Це неправда лише тому, що git порівнює з останнім, що знав про GitHub. Спершу git pull, і лише потім нова гілка lr4 - інакше вона почнеться без ЛР3.

3. Approve власного PR. Документація GitHub: «Pull request authors cannot approve their own pull requests». Для схвалення потрібна друга людина з доступом до репо (Settings → Collaborators, не перевірено). gh pr review 2 --approve зі свого акаунта теж не пройде. Для своїх лаб досить Comment собі ж.

4. Дописав коміт у lr3 після злиття PR. Ці коміти в main не підуть - PR уже закритий. Онови main (git pull) і зроби нову гілку і новий PR.

Як роблять профі

  • Кожна зміна - через PR, навіть у соло-проєктах: видно, що і навіщо змінено (Creating a pull request).
  • У налаштуваннях репо вмикають Automatically delete head branches (Settings → General → Pull Requests) - гілка зникає сама після злиття (docs).
  • Захищають main правилами (ruleset): зливати лише через PR з Approve; сторінка документації називає плани Team і Enterprise, тож на безкоштовному плані для приватного репо, схоже, недоступно (не перевірено) (About rulesets).
  • Багато команд обирають Squash and merge: в main один акуратний коміт на PR (About pull request merges).
  • У описі PR пишуть Closes #N - issue закриється при злитті (урок 10).
  • Злиття з терміналу: gh pr merge 2 --squash --delete-branch (gh pr merge).

Для лаб

Для лаб: у univer-labs кожна лаба - своя гілка lr1 ... lr7. Коли лаба готова - PR lr3 → main з описом «що зроблено, які завдання проходять doctest» і Closes #N, якщо закриваєш issue. Перед здачею кинь викладачу посилання на PR: там видно всі зміни лаби одним списком у Files changed. Зливай звичайною кнопкою Merge pull request (Create a merge commit): у main лишаються всі коміти лаби - коміт на крок, як у «Лаби в git», - плюс коміт злиття, по якому видно, де була гілка lr3. Після злиття - git switch main, git pull, git branch -d lr3.

Squash and merge - теж можна, якщо хочеш коротку історію: одна лаба = один коміт у main. Але окремих кроків «завдання 1», «завдання 2» в main тоді не буде, а git branch -d lr3 після squash може відмовити (Типова помилка 1) - видаляй git branch -D lr3, коли PR злитий.

Відповіді
  1. Прохання на GitHub злити гілку в main. Видно всі зміни (Files changed), можна обговорити кожен рядок і дати схвалення до злиття.
  2. Comment, Approve, Request changes. Автор PR не може схвалити свій PR - зі свого акаунта в нього лише Comment.
  3. Merge commit: усі коміти гілки + коміт злиття з двома батьками. Squash: лише один новий коміт «Назва (#2)».
  4. Коміти lr3 не потрапили в main, там новий squash-коміт. А origin/lr3 уже прибрано (Delete branch на сайті + git fetch --prune), тож -d порівнює з main і не знаходить там комітів lr3. Якщо PR злитий на сайті - git branch -D lr3. (Поки origin/lr3 ще є, -d лише попередив би і видалив, код 0.)
  5. git switch main, git pull, git branch -d lr3, і git fetch --prune (або git push origin --delete lr3, якщо на сайті гілку не видалив).
