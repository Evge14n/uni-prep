Тема 14. Теги - позначити здачу

Навіщо: ти здав ЛР1, а через тиждень ще щось у ній підправив. Викладач питає: «А що саме ти показував мені на парі?» Тег - це наліпка lr1-zdano на коміт, який ти здав. Вона не зсувається, тож відповідь завжди одна команда.

Коротко

Тег - назва, яку назавжди приклеїли до одного коміту. Гілка (Урок 07) - теж назва коміту, але вона їде вперед з кожним новим комітом. Тег стоїть на місці.

                           lr1-zdano (тег - стоїть)
                               │
  a1b2c3d ──── 73942e5 ──── baa1934 ──── 99d1fc7
                                            │
                                          main (гілка - їде вперед з кожним комітом)

Аналогія: гілка - закладка, яку ти перекладаєш на сторінку, де зупинився. Тег - наліпка «здав тут» на конкретній сторінці.

Теги бувають двох видів:

Вид Як створити Що зберігає Коли брати
легкий git tag lr1-chernetka лише назву → коміт для себе, на хвилину
анотований git tag -a lr1-zdano -m "ЛР1 здано" назву, автора, дату, повідомлення здача, версія - усе, що бачать інші
Команда Що робить
git tag список тегів
git tag -n список з першим рядком повідомлення
git tag -a lr1-start -m "..." HEAD~1 тег на старіший коміт (тут - на попередній)
git show lr1-zdano хто, коли і з яким повідомленням поставив тег + сам коміт
git push --follow-tags пушить коміти і анотовані теги (легкі - ні!)
git push origin lr1-zdano пушить один тег будь-якого виду
git tag -d lr1-chernetka видалити тег у себе
git push origin --delete lr1-chernetka видалити тег на GitHub
git checkout lr1-zdano подивитися файли, якими вони були на здачі (detached HEAD, нижче)

Головне правило: звичайний git push тегів не пушить. Тег живе лише у тебе, поки ти не відправиш його окремо.

Передбач, потім запусти

  1. У тебе два нові коміти, ти їх уже запушив. Тепер git tag -a lr1-zdano -m "ЛР1 здано викладачу" і git push. Що напише git push і чи буде тег на GitHub?

    Відповідь ```text Everything up-to-date ``` Тегу на GitHub **нема**: `git push` без прапорців відправляє лише гілку, а нових комітів у ній нема. Тег треба відправити окремо (крок 4 у «Руками»).

  2. Є легкий тег lr1-chernetka і анотований lr1-zdano на тому самому коміті. Запускаєш git push --follow-tags. Скільки тегів поїде на GitHub?

    Відповідь Один - `lr1-zdano`. `--follow-tags` бере лише **анотовані** теги. Легкий доведеться пушити окремо: `git push origin lr1-chernetka`.

  3. git checkout lr1-zdano - на якій гілці ти опинишся?

    Відповідь Ні на якій. git напише `You are in 'detached HEAD' state` - «HEAD відчеплений»: ти стоїш на коміті, а не на гілці. Дивитися можна, комітити - краще ні (див. «Типові помилки»). Назад: `git switch main`.

  4. Тег lr1-zdano уже є. Ти виправив опечатку і знову пишеш git tag -a lr1-zdano -m "ЛР1 здано ще раз". Що буде?

    Відповідь ```text fatal: tag 'lr1-zdano' already exists ``` Код виходу 128, нового тегу нема. Два теги з однією назвою бути не може.

Руками

Пісочниця - клон ~/pisochnytsia з Уроку 03. Хеші комітів у тебе будуть інші - це нормально.

Крок 1. Два коміти «лаби» і push.

cd ~/pisochnytsia
printf 'print("ЛР1, завдання 1")\n' > lr1.py
git add lr1.py
git commit -m "ЛР1: завдання 1"
printf 'print("ЛР1, завдання 2")\n' >> lr1.py
git commit -am "ЛР1: завдання 2"
git push

Нове тут:

  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • printf - друкує текст за шаблоном; \n - Enter. Назва: print formatted - «надрукувати за шаблоном».
  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт).
  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати»: зберегти знімок змін в історію. -m - повідомлення коміту одразу в команді; без -m відкриється nano; -a - спершу сам додає зміни ВЖЕ відстежуваних файлів; нові файли - ні.
  • git push - відправляє твої коміти на GitHub. Назва: push - «штовхнути»: відправити свої коміти на GitHub.
  • ~ - домашня тека /home/evgen. Назва: tilde («тильда») - домашня тека.
  • "..." - текст з пробілами одним словом, $ підставляється. Назва: подвійні лапки - «усе це одне слово, але $ працює».
  • '...' - текст буквально, нічого не підставляється. Назва: одинарні лапки - «буквально, як написано».
  • > - пише вивід у файл, старий вміст стирає. Назва: redirect - «перенаправлення» виводу у файл.
  • >> - дописує вивід у кінець файлу. Назва: append - «дописати» в кінець файлу.

Усе про кожну команду - у вкладці «Команди», а тут торкнись команди в коді - вискочить підказка.

Крок 2. Легкий і анотований тег.

git tag lr1-chernetka
git tag -a lr1-zdano -m "ЛР1 здано викладачу"
git tag
git tag -n

lr1-chernetka
lr1-zdano
lr1-chernetka   ЛР1: завдання 2
lr1-zdano       ЛР1 здано викладачу

Нове тут:

  • git tag - ставить на коміт мітку з назвою (напр. lr1-zdano). Назва: tag - «мітка, ярлик». -a - анотований тег: з автором, датою і описом (для здачі - саме такий); -m - опис анотованого тегу; без -m git відкриє nano; -n - у списку тегів показати й перший рядок опису. git tag -n для легкого тегу показує повідомлення коміту (своє в нього нема), для анотованого - повідомлення тегу.

Крок 3. Чим вони різні всередині.

git show lr1-zdano --stat

 lr1.py | 1 +

Нове тут:

  • git show - показує один коміт з його змінами або старий файл. Назва: show - «показати». --stat - замість рядків змін - лише які файли змінено і скільки рядків; lr1-zdano - тег: покаже, що саме було здано (урок 14 курсу Git). У дужках після хешу коміту - які гілки й теги на ньому стоять (як у git log --decorate нижче). Спершу йде сам тег (хто поставив, коли, навіщо), потім коміт. git show lr1-chernetka --stat одразу починається з commit - у легкого тегу нема ні автора, ні дати.

Ще одна перевірка - якого типу обʼєкт стоїть за назвою:

git cat-file -t lr1-chernetka
git cat-file -t lr1-zdano
git log --oneline --decorate -n 2

commit
tag
baa1934 (HEAD -> main, tag: lr1-zdano, tag: lr1-chernetka, origin/main, origin/HEAD) ЛР1: завдання 2
73942e5 ЛР1: завдання 1

Нове тут:

  • git cat-file - показує тип або вміст обʼєкта git (коміт, тег). Назва: cat file - «вивести обʼєкт» (cat - від concatenate, «зчепити»). -t - тип обʼєкта: commit (коміт), tag (анотований тег), tree (тека), blob (файл).
  • git log - показує історію комітів, новий зверху. Назва: log - «журнал»: історія комітів. --oneline - по рядку на коміт: 7 знаків хешу і перший рядок повідомлення; --decorate - показати біля комітів назви гілок і тегів (у терміналі і так увімкнено); -n - лише N останніх комітів: -n 3 (або коротко -3). Легкий тег - просто назва коміту. Анотований - окремий обʼєкт tag у репозиторії, який вказує на коміт. --decorate дописує в дужках, які гілки й теги стоять на коміті (у терміналі git log --oneline робить це й сам).

Крок 4. Відправити теги на GitHub.

git push --follow-tags
git ls-remote --tags origin

To github.com:Evge14n/pisochnytsia.git
 * [new tag]         lr1-zdano -> lr1-zdano
d0e7a5c2ff6b6ed977afd50e6136c51b1a49219c    refs/tags/lr1-zdano
baa1934646dbbd7c5cf498cb02332e01ec470396    refs/tags/lr1-zdano^{}

Нове тут:

  • git push: --follow-tags - разом з комітами відправити й анотовані теги на них (легкі - ні).
  • git ls-remote - показує, які гілки й теги є на GitHub. Назва: ls remote - «перелічити на віддаленому»: що лежить на GitHub. --tags - лише теги; origin - яке віддалене репо питати (зазвичай origin). git ls-remote --tags origin питає GitHub, які теги там. Є лише lr1-zdano: легкий --follow-tags не взяв. Рядок з ^{} - коміт, на який вказує анотований тег. Легкий відправляємо окремо:
git push origin lr1-chernetka

To github.com:Evge14n/pisochnytsia.git
 * [new tag]         lr1-chernetka -> lr1-chernetka

Нове тут:

  • git checkout - старе «перемкнути гілку або повернути файл» (тепер switch і restore). Назва: check out - «взяти» (як книжку в бібліотеці). lr1-zdano - тег: подивитись, що було здано (стан «відʼєднаний HEAD»), назад - git switch main.
  • git status - показує, що змінено і що піде в наступний коміт. Назва: status - «стан». Переклад: «Ти у стані відчепленого HEAD. Можна дивитися і навіть комітити, але ці коміти не належать жодній гілці. Хочеш їх зберегти - створи гілку git switch -c назва. Повернутися - git switch -». Тут можна відкрити файли, запустити doctest - побачиш рівно те, що здавав. Назад на гілку:
git switch main

Нове тут:

  • git switch - перемикає на іншу гілку (-c - створює нову). Назва: switch - «перемкнути».

Крок 6. Тег на старіший коміт. Забув поставити тег одразу? Його можна поставити на будь-який коміт:

git tag -a lr1-start -m "Почав ЛР1" HEAD~1
git tag -l "lr1-z*"

Нове тут:

  • git tag: -l - лише теги за шаблоном: git tag -l "lr1-*". HEAD~1 - коміт перед поточним (можна і хеш з git log --oneline). git tag -l "lr1-z*" показує лише теги, що починаються на lr1-z, - тут це lr1-zdano.

Крок 7. Видалити тег у себе і на GitHub:

git tag -d lr1-chernetka
git push origin --delete lr1-chernetka

Deleted tag 'lr1-chernetka' (was baa1934)
To github.com:Evge14n/pisochnytsia.git
 - [deleted]         lr1-chernetka

Нове тут:

  • git tag: -d - видалити тег у себе (на GitHub - окремо: git push origin --delete ТЕГ).
  • git push: --delete - видалити гілку або тег на GitHub: git push origin --delete lr3. Видаляй лише свої чернеткові теги. Тег здачі, який уже бачив викладач, не чіпай (чому - у «Типових помилках»).

Releases на GitHub (коротко). На сторінці репо справа є Releases → Draft a new release → Choose a tag (вибрати lr1-zdano) → назва і опис → Publish release. Реліз - це тег + сторінка з описом і архівами Source code (zip) / Source code (tar.gz). Для лаб досить тегу, реліз - для програм, які хтось завантажує.

Для лаб: після здачі кожної лаби - анотований тег lr1-zdano ... lr7-zdano і git push origin lr1-zdano. Тоді навіть через пів року git checkout lr3-zdano покаже рівно те, що бачив викладач, а git diff lr3-zdano main - що ти міняв після здачі. Як це вбудувати в роботу з лабами - файл «Лаби в git - univer-labs покроково».

Типові помилки

  1. Тег не зʼявився на GitHub. Ти зробив git push, а він написав Everything up-to-date. Звичайний push теги не везе. Виправлення: git push origin lr1-zdano (будь-який тег) або git push --follow-tags (лише анотовані).

  2. fatal: tag 'lr1-zdano' already exists - назва зайнята. Якщо тег ще не пушив - git tag -d lr1-zdano і створи знову. Якщо вже на GitHub і його бачив викладач - не пересувай (його клони мають старий, і ви говоритимете про різні версії). Краще новий тег: lr1-zdano-2 з повідомленням, що змінено.

  3. git switch на тег не працює: text fatal: a branch is expected, got tag 'lr1-zdano' hint: If you want to detach HEAD at the commit, try again with the --detach option. switch переходить лише на гілки. На тег - git switch --detach lr1-zdano або git checkout lr1-zdano.

  4. Коміт у detached HEAD «зник». Ти на тезі зробив коміт і пішов на main. git попереджає: ```text Warning: you are leaving 1 commit behind, not connected to any of your branches:

    99d1fc7 Правка на тезі

If you want to keep it by creating a new branch, this may be a good time to do so with:

git branch <new-branch-name> 99d1fc7

Одразу після цього коміт ще можна врятувати гілкою: `HEAD@{1}` - «де HEAD був один крок тому» (reflog, Урок 12).bash git branch lr1-pravka HEAD@{1} ```

Нове тут:

  • git branch - показує, створює і видаляє гілки. Назва: branch - «гілка». Правило: хочеш щось правити у старій версії - спершу git switch -c нова-гілка, потім комітить.
  1. fatal: no tag message? - написав git tag -a lr1-test без -m, git відкрив nano, а ти вийшов, нічого не написавши. Тег не створено. Пиши відразу з -m "повідомлення".

Як роблять профі

  • Версії у форматі v1.4.2 (Semantic Versioning): більша цифра - зламана сумісність, середня - нова можливість, менша - виправлення. Тег v1.4.2 = випуск програми. https://semver.org
  • Лише анотовані теги для випусків. Pro Git: «It's generally recommended that you create annotated tags», легкі - для тимчасових міток. Профі часто ще й підписують тег ключем: git tag -s (GitHub показує «Verified»).
  • push.followTags - щоб не забувати теги, один раз: bash git config --global push.followTags true

Нове тут:

  • git config - читає і змінює налаштування git (імʼя, пошта, редактор). Назва: config - від configuration, «налаштування». --global - для тебе на цьому ноутбуці: пише у файл ~/.gitconfig, діє в усіх репо. Після цього звичайний git push сам везе нові анотовані теги (перевірено в 2.43.0).
  • Release з терміналу через gh (Урок 16): gh release create lr1-zdano --title "ЛР1" --notes-from-tag --verify-tag
  • сторінка релізу з повідомленням тегу; --verify-tag не дасть створити реліз, якщо тегу ще нема на GitHub. bash gh release create lr1-zdano --title "ЛР1" --notes-from-tag --verify-tag

Нове тут:

  • gh release create - робить на GitHub сторінку релізу для тегу. Назва: release create - «створити випуск (реліз)» на GitHub. --title - назва релізу на сайті, напр. --title "ЛР1"; --notes-from-tag - опис релізу взяти з повідомлення анотованого тегу (git tag -a ... -m ...); --verify-tag - не створювати реліз, якщо такого тегу ще нема на GitHub (спершу git push origin ТЕГ); lr1-zdano - тег, для якого реліз (з Git уроку 14).
  • Захист тегів у командах: правило (ruleset) на GitHub забороняє видаляти й пересувати теги v* (docs.github.com, «About rulesets»).

Самоперевірка

  1. Чим тег відрізняється від гілки?
  2. Чому для здачі краще анотований тег, а не легкий?
  3. Ти зробив git tag -a lr2-zdano -m "ЛР2 здано" і git push. Викладач не бачить тегу на GitHub. Чому і що зробити?
  4. Що означає detached HEAD і як повернутися назад?
  5. Як подивитися, які теги є на GitHub, не відкриваючи сайт?
Відповіді
  1. Гілка їде вперед з кожним новим комітом, тег назавжди стоїть на одному коміті.
  2. Анотований зберігає автора, дату і повідомлення («ЛР2 здано»), це окремий обʼєкт; його бере git push --follow-tags. Легкий - лише назва, без «хто і коли».
  3. Звичайний git push теги не пушить. git push origin lr2-zdano (або git push --follow-tags).
  4. HEAD стоїть на коміті, а не на гілці (після git checkout тег). Нові коміти тут не належать жодній гілці. Назад - git switch main (або git switch -).
  5. git ls-remote --tags origin.
