Тема 15. GitHub Pages

Навіщо: GitHub може сам показати твій файл index.html як сайт за адресою https://evge14n.github.io/.... Так зроблено твій сайт підготовки uni-prep. Сьогодні зробиш свою першу сторінку з фізики - без сервера і без грошей.

Коротко

GitHub Pages - безкоштовний хостинг статичних сторінок: GitHub бере HTML, CSS і JavaScript з репозиторію і показує їх як сайт. «Статичний» - сторінка лежить готовим файлом; Python, PHP на сервері Pages не запускає (docs: «GitHub Pages does not support server-side languages such as PHP, Ruby, or Python»).

 ноутбук                       GitHub                                   інтернет
 index.html ── git push ──→  репо fizyka-storinka (main)  ── Pages ──→  https://evge14n.github.io/fizyka-storinka/
                              Settings → Pages:                         (бачать УСІ)
                              Deploy from a branch, main, / (root)

Аналогія: репо - твій зошит, Pages - стенд у коридорі, куди автоматично вивішується копія сторінки з зошита. Стенд бачать усі, хто проходить повз.

Що Як
хто може на GitHub Free - лише публічний репо (docs: «If the account that owns the repository uses GitHub Free ..., the repository must be public»). Це обмеження тарифу: на платному Pro можна і з приватного, але сам сайт однаково публічний (docs: «GitHub Pages sites are publicly available on the internet, even if the repository for the site is private»)
що показується index.html (або index.md, README.md) у корені вибраної гілки й теки
адреса сайту проєкту https://evge14n.github.io/НАЗВА-РЕПО/ (логін малими літерами)
сайт користувача окремий репо з назвою evge14n.github.io → адреса https://evge14n.github.io/
скільки чекати «up to 10 minutes» після push (docs); на практиці частіше близько хвилини
де статус вкладка Actions репо → запуск pages build and deployment (зелена галочка = готово)

Тому сайт - окремий публічний репо (наприклад fizyka-storinka), а лаби лишаються в приватному univer-labs.

Передбач, потім запусти

  1. Ти створив index.html у клоні і нічого більше не робив. Що покаже git status --short?

    Відповідь > **Нове тут:** > > - `git status` - показує, які файли змінено і що піде в наступний коміт (збережений знімок). `--short` - коротко: по рядку на файл з двома буквами стану (`M`, `A`, `??`) (short - «коротко»). > > **Як читати:** > > - Слово з мінусом (як `-m` тут) - **прапорець**: уточнює, що саме зробити команді. > - Якщо поруч у дужках стоїть довга назва з двома мінусами - це той самий прапорець, пиши будь-яку одну. > - Короткі можна склеювати: `-am` = `-a` і `-m`. > - Символи `~` `>` набирай в англійській розкладці (`~` - Shift і клавіша ліворуч від 1). > > Усе про кожну команду - у вкладці [«Команди»](#/u/prog/komandy), а тут торкнись команди в коді - вискочить підказка. ```text ?? index.html ``` `??` - файл новий, git за ним ще не стежить. Pages бачить лише те, що **запушено** на GitHub.

  2. Репо створено з README (1 коміт). Ти закомітив index.html, запушив, потім закомітив зміну привітання і знову запушив. Скільки комітів у origin/main і яку версію покаже сайт через кілька хвилин?

    Відповідь Комітів 3 (перевірка: `git rev-list --count origin/main`). Сайт покаже останню запушену версію - з новим привітанням: Pages завжди бере те, що зараз лежить у вибраній гілці на GitHub.

Нове тут:

  • git rev-list - перелічує або рахує збережені знімки (коміти) гілки. Назва: rev list - від revision list, «список версій» (версія = коміт). --count - лише число комітів, без списку (count - «порахувати»); origin/main - скільки комітів на GitHub (те, що знав останній git fetch).
  1. Ти випадково закомітив файл з паролем, а потім зробив git rm і ще один коміт. Пароля в репо вже нема?
    Відповідь > **Нове тут:** > > - `git rm` - видаляє файл з диска і git; `--cached` - лише з git. Є. Його нема в **останньому** коміті, але в історії він лишився: `git show HEAD~1:parol.txt` його покаже. У публічному репо історію бачать усі. Тому секрети в репо не кладуть **взагалі** (див. «Типові помилки»).

Нове тут:

  • git show - показує один збережений знімок (коміт) зі змінами або старий файл.

Руками

Хеші комітів у тебе будуть інші.

Крок 1. Публічний репо на сайті. Справа вгорі + → New repository → Repository name: fizyka-storinka → Public → Add README: On → Create repository. (Через gh, Урок 16: gh repo create fizyka-storinka --public --add-readme.)

Нове тут:

  • gh repo create - створює новий репозиторій (сховище коду) на GitHub з терміналу. Назва: gh - gh - від GitHub; офіційна програма GitHub CLI (CLI - «командний рядок»); repository create - «створити репозиторій» на GitHub. --public - публічний: бачать усі (портфоліо, GitHub Pages) (public - «відкритий»); --add-readme - одразу створити файл README.md - опис проєкту.

Клонуй і створи сторінку:

git clone git@github.com:Evge14n/fizyka-storinka.git ~/fizyka-storinka
cd ~/fizyka-storinka
nano index.html

Нове тут:

  • git clone - копіює весь проєкт з історією з GitHub до тебе.
  • ~ (tilde) - твоя домашня тека, /home/evgen.
  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • nano - простий редактор файлів у терміналі. Назва: nano - жарт з одиницями: наступник редактора pico (піко < нано).

Набери в nano (Ctrl+O, Enter - зберегти; Ctrl+X - вийти):

<!doctype html>
<html lang="uk">
<head>
  <meta charset="utf-8">
  <title>Фізика - Імʼя</title>
</head>
<body>
  <h1>Привіт! Це моя сторінка з фізики</h1>
  <p>1 курс, фізичний факультет ЛНУ.</p>
  <p>Тут будуть конспекти й корисні посилання.</p>
</body>
</html>

Що тут що: <h1> - великий заголовок, <p> - абзац, <title> - назва вкладки браузера. <meta charset="utf-8"> каже браузеру, що текст у UTF-8 - без нього кирилиця може стати «кракозябрами». Подивитися локально, до GitHub:

xdg-open index.html

Нове тут:

  • xdg-open - відкриває файл у його звичайній програмі. Назва: XDG (X Desktop Group, нині freedesktop.org) + open - «відкрити».

Крок 2. Коміт і push.

git add index.html
git commit -m "Перша сторінка"
git push
git ls-files

[main 3db7e8b] Перша сторінка
 1 file changed, 12 insertions(+)
 create mode 100644 index.html
To github.com:Evge14n/fizyka-storinka.git
   f8c0af1..3db7e8b  main -> main
README.md
index.html

Нове тут:

  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт).
  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати». -m (--message) - повідомлення коміту одразу в команді; без -m відкриється nano (message - «повідомлення»).
  • git push - відправляє твої нові знімки (коміти) з компʼютера на GitHub. Назва: push - «штовхнути».
  • git ls-files - перелічує файли, за якими стежить git (що є в репо). Назва: ls files - «перелічити файли» (ls - від list, «список»).
  • "..." (double quotes) - усе між лапками - одне слово, навіть з пробілами.

git ls-files - які файли в репо. index.html має бути в корені (без теки перед назвою).

Крок 3. Увімкнути Pages на сайті. У репо fizyka-storinka:

Settings → (ліве меню, розділ «Code, planning, and automation») Pages
  → Build and deployment → Source: Deploy from a branch
  → Branch: main    тека: / (root)    → Save

(Назви пунктів - з docs.github.com, «Configuring a publishing source for your GitHub Pages site», відкрито 18.11.2026.)

Крок 4. Дочекатися і відкрити. Вкладка Actions у репо → там зʼявиться запуск pages build and deployment. Жовтий кружечок - ще йде, зелена галочка - готово, червоний хрестик - помилка (клікни, щоб побачити яку). Документація: «It can take up to 10 minutes for changes to your site to publish after you push the changes to GitHub». Для прикладу: у публічного репо mmistakes/minimal-mistakes такі запуски 2026 року тривали близько 50 секунд (GitHub API, перевірено 18.11.2026). Коли готово - Settings → Pages → Visit site, або відкрий адресу:

https://evge14n.github.io/fizyka-storinka/

Перевірити з терміналу, чи сайт уже живий (200 - є, 404 - ще нема):

curl -s -o /dev/null -w '%{http_code}\n' https://evge14n.github.io/fizyka-storinka/

Нове тут:

  • curl - звертається до сайту за адресою і показує відповідь. Назва: client URL - «клієнт для URL» (URL - адреса в інтернеті). -s (--silent) - тихо: без смужки прогресу і без повідомлень curl (silent - «тихо»); -o (--output) - записати відповідь у файл замість екрана; -o /dev/null - просто викинути її (output - «вивід»); -w (--write-out) - після завершення надрукувати те, що просиш, напр. '%{http_code}\n' - код відповіді сервера (write-out); /dev/null - «чорна діра»: усе, що туди записати, зникає.
  • '...' (single quotes) - текст буквально: $, * і пробіли всередині - звичайні символи.

Для твого uni-prep 18.11.2026 це дало 200, а для ще не створеної fizyka-storinka - 404:

curl -s -o /dev/null -w '%{http_code}\n' https://evge14n.github.io/uni-prep/

Крок 5. Оновити сторінку. Кожен push у main = новий запуск і нова версія сайту.

sed -i 's/Привіт!/Вітаю!/' index.html
git diff
git commit -am "Змінив привітання"
git push

Нове тут:

  • sed - друкує потрібні рядки або замінює текст. Назва: stream editor - «потоковий редактор». -i (--in-place) - змінити САМ файл (без -i sed лише показує); -i.bak - ще й копія (in-place - «на місці»).
  • git diff - показує, які рядки змінено (+ додано, - прибрано).
  • git commit: -a (--all) - спершу сам додає зміни ВЖЕ відстежуваних файлів; нові файли - ні (all - «усі»).

git diff покаже:

-  <h1>Привіт! Це моя сторінка з фізики</h1>
+  <h1>Вітаю! Це моя сторінка з фізики</h1>

За хвилину онови сторінку в браузері (Ctrl+Shift+R - без старої копії з кешу).

Крок 6. .nojekyll (коротко). Коли Pages публікує з гілки, він пропускає файли через Jekyll - програму, що збирає сайти. Jekyll не публікує файли й теки, назва яких починається з _, . або # (docs, «About GitHub Pages and Jekyll»). Якщо в тебе тека _images чи файл _dani.json і на сайті вони «зникли» - поклади в корінь порожній файл .nojekyll, і Jekyll вимкнеться (docs: «disable the Jekyll build process by creating an empty file called .nojekyll in the root of your publishing source»).

touch .nojekyll
git add .nojekyll
git commit -m "Без Jekyll"
git push

Нове тут:

  • touch - створює порожній файл; якщо файл уже є - вміст не чіпає. Назва: touch - «торкнутися» файлу.

touch створює порожній файл. Крапка на початку = прихований файл: звичайний ls його не покаже, ls -a - покаже.

Нове тут:

  • ls - показує, що лежить у теці. Назва: list - «список» (вмісту теки). -a (--all) - показати й приховані (назва з крапки), разом з . і .

Приклад - твій uni-prep. https://evge14n.github.io/uni-prep/ - це репо Evge14n/uni-prep, публічне. Він публікується не «з гілки», а другим пунктом того ж меню - Source: GitHub Actions, своїм файлом .github/workflows/pages.yml (видно через GitHub API, 18.11.2026). Для простої сторінки «з гілки» досить, Actions потрібні, коли сайт треба спершу зібрати програмою.

Що НЕ класти в репо сайту (його бачить увесь інтернет, і вся історія комітів теж): - паролі, токени, ключі (~/.ssh/id_ed25519 - ніколи), файли .env; - оцінки, бали, списки групи, телефони й пошти одногрупників - це чужі особисті дані; - розвʼязки лаб, поки їх не здали (одногрупник скопіює - питання будуть до обох). Docs: «GitHub Pages sites are publicly available on the internet» і «shouldn't be used for sensitive transactions like sending passwords or credit card numbers».

Для лаб: самі лаби - у приватному univer-labs, бо Pages на Free працює лише з публічних репо, а розвʼязки до здачі показувати всім не можна. Pages знадобиться для іншого: сторінка-портфоліо, конспект з графіками, сайт команди на хакатоні. Навичка та сама - git add, git commit, git push, і через хвилину сайт оновився.

Типові помилки

  1. Пункту Pages нема або він просить змінити план - репо приватний. На GitHub Free Pages лише для публічних. Зроби окремий публічний репо для сайту (не робити публічним univer-labs!). Точний текст на сторінці Settings → Pages для приватного репо - (не перевірено).

  2. 404 «Site not found · GitHub Pages» (так називається сторінка-заглушка, перевірено curl 18.11.2026). Причини: - сайт ще будується - глянь Actions, почекай; - Pages не ввімкнено (крок 3) або вибрано не ту гілку чи теку; - index.html не в корені (git ls-files показує site/index.html) або названий Index.html - на сервері великі й малі літери різні; - помилка в адресі: потрібна https://evge14n.github.io/fizyka-storinka/, а не github.com/Evge14n/....

  3. Сайт не змінився - забув push. Коміт є лише в тебе. git status скаже: text Your branch is ahead of 'origin/main' by 1 commit. (use "git push" to publish your local commits) Виправлення: git push, потім Actions і оновити сторінку з Ctrl+Shift+R.

  4. Видалив секрет новим комітом - а він лишився. Перевір на локальній пісочниці (нічого не пушимо): bash git init ~/sekret-demo cd ~/sekret-demo printf 'пароль=qwerty123\n' > parol.txt git add parol.txt git commit -m "Додав пароль" git rm parol.txt git commit -m "Прибрав пароль" git show HEAD~1:parol.txt text пароль=qwerty123

Нове тут:

  • git init - робить теку репозиторієм git (створює .git). Назва: init - від initialize, «почати, підготувати».
  • printf - друкує текст; \n у ньому - Enter (новий рядок). Назва: print formatted - «надрукувати за шаблоном».
  • > (redirect) - пише вивід у файл, старий вміст стирає.

Файлу нема в теці, але старий коміт його памʼятає. Якщо справжній пароль чи токен потрапив на GitHub - спершу зміни сам пароль/токен (вважай його вкраденим), а вже потім думай про чистку історії.

Як роблять профі

  • Pages через GitHub Actions замість «з гілки»: сайт збирається програмою (Vite, Hugo, MkDocs) і публікується окремим кроком - як твій uni-prep. Docs, «Configuring a publishing source for your GitHub Pages site».
  • Генератори статичних сайтів: Markdown → гарний сайт. Для документації Python-проєктів часто беруть MkDocs (https://www.mkdocs.org), для блогів - Jekyll або Hugo.
  • Свій домен замість github.io (наприклад evgen.dev) - Settings → Pages → Custom domain (docs, «Configuring a custom domain for your GitHub Pages site»).
  • Секрети ніколи не в коді: у публічних репо GitHub безкоштовно сам шукає токени й ключі (secret scanning: «Public repositories: Secret scanning runs automatically for free»), а push protection «blocks pushes that contain secrets» - docs, «About secret scanning» і «About push protection». Але це страховка, а не дозвіл.
  • Ліміти Pages: сайт до 1 ГБ, мʼякий ліміт 100 ГБ трафіку на місяць і 10 збірок на годину (docs, «GitHub Pages limits»). Для сторінки з фізики це дуже багато.

Відповіді
  1. На Free Pages працює лише з публічних репо, а лаби до здачі не мають бути публічними. Сайт - окремий публічний репо.
  2. index.html у корені гілки main (git ls-files показує просто index.html).
  3. https://evge14n.github.io/fizyka-storinka/.
  4. git status (чи нема «ahead» - чи справді запушено) → вкладка Actions, запуск «pages build and deployment» (жовтий - чекати, червоний - помилка) → оновити сторінку з Ctrl+Shift+R.
  5. Вимикає Jekyll: тоді на сайт потрапляють і файли/теки, що починаються з _ (наприклад _images).
