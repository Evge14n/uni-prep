Тема 16. gh - GitHub з терміналу

Навіщо: щоб створити Issue, відкрити Pull Request чи злити його, не треба йти в браузер. Пишеш лабу в терміналі - там же й gh pr create. Для ЛР2 це «закінчив завдання → PR → злив» за три команди.

Нове тут:

  • gh pr create - створює на GitHub запит злити твою гілку в main (PR). Назва: gh - gh - від GitHub; офіційна програма GitHub CLI (CLI - «командний рядок»); pr - pull request, «запит на злиття» гілки в main; create - «створити».

Як читати:

  • Слово з мінусом (як -d тут) - прапорець: уточнює, що саме зробити команді.
  • Якщо поруч у дужках стоїть довга назва з двома мінусами - це той самий прапорець, пиши будь-яку одну.
  • Символи ~ > * набирай в англійській розкладці (~ - Shift і клавіша ліворуч від 1).

Усе про кожну команду - у вкладці «Команди», а тут торкнись команди в коді - вискочить підказка.

Коротко

git працює з репозиторієм (коміти, гілки, push). gh (GitHub CLI) працює з сайтом GitHub: Issues, Pull Requests, налаштування репо, Actions. gh сам дивиться в git remote поточної теки і розуміє, з яким репо ти працюєш.

Нове тут:

  • git remote - показує і задає, де лежить твій проєкт на GitHub (origin). Назва: remote - «віддалений»: репо на іншому компʼютері (GitHub).
 термінал ── git push / pull ─────→  репозиторій на GitHub (коміти, гілки)
          └─ gh issue / pr / repo ─→  сайт GitHub (Issues, PR, налаштування) - через API

Аналогія: git - як носити зошит у деканат і назад; gh - як телефонувати в деканат: «створіть заявку», «закрийте заявку».

Команда Що робить
gh auth status чи ти увійшов і яким акаунтом
gh repo view / gh repo view --web опис і README поточного репо / те саме в браузері
gh repo clone Evge14n/НАЗВА клонувати (коротше за git clone git@github.com:...)
gh repo create НАЗВА --private створити репо (--public, --add-readme, --clone, --source=. --push)
gh issue create / list / view 1 / close 1 Issues: створити, список, подивитися №1, закрити №1
gh pr create --fill PR з поточної гілки, назва й опис - з комітів
gh pr list / view 1 / diff 1 список PR, PR №1, його зміни
gh pr checkout 1 забрати гілку PR №1 до себе (щоб перевірити)
gh pr merge 1 --squash --delete-branch злити PR №1 одним комітом і видалити гілку тут і на GitHub
gh browse відкрити репо в браузері (gh browse lr2_1.py - конкретний файл)
gh help, gh pr merge --help довідка (англійською, з прикладами)

Нове тут:

  • gh auth status - показує, чи gh увійшов у GitHub і яким акаунтом. Назва: auth - від authentication, «вхід»; status - «стан».
  • gh repo view - показує опис і README репозиторію (або відкриває його в браузері). Назва: repository view - «переглянути репозиторій». --web - відкрити сторінку репо в браузері замість друку в терміналі (web - «вебсторінка»).
  • gh repo clone - завантажує собі копію проєкту (репозиторію) з GitHub, як git clone. Назва: repository clone - «клонувати репозиторій» (сховище коду).
  • gh repo create - створює новий репозиторій (сховище коду) на GitHub з терміналу. Назва: repository create - «створити репозиторій» на GitHub. --private - приватний репо: бачиш лише ти (і кого запросиш); для лаб - саме так (private - «приватний»).
  • gh issue create - створює на GitHub завдання чи зауваження (Issue) у репо. Назва: issue - «питання, справа».
  • gh pr create: --fill - назву й опис узяти з комітів гілки (fill - «заповнити»).
  • gh pr list - показує список запитів на злиття (PR) на GitHub. Назва: pr - pull request, «запит на злиття»; list - «список».
  • gh pr checkout - забирає гілку чужого запиту (PR) до себе і перемикає на неї. Назва: pr - pull request; check out - «взяти» (як книжку в бібліотеці). 1 - номер PR; можна і назву гілки.
  • gh pr merge - зливає запит (PR) у main на GitHub, як кнопка Merge. Назва: pr - pull request; merge - «злити». --squash - усі коміти PR одним комітом на main (Squash and merge) (squash - «зчавити»); --delete-branch - після злиття видалити гілку і на GitHub, і в тебе (delete branch - «видалити гілку»); --help - довідка з усіма прапорцями (help - «допомога»).
  • gh browse - відкриває сторінку проєкту (чи файлу) на GitHub у браузері. Назва: browse - «переглядати». lr2_1.py - відкрити цей файл на GitHub.
  • gh help - показує довідку gh (англійською).
  • git clone - копіює весь проєкт з історією з GitHub до тебе.
  • diff - показує, чим відрізняються два файли. Назва: difference - «різниця».

Чому gh з офіційного репо GitHub, а не з Менеджера програм Mint. У репозиторії Mint/Ubuntu лежить gh 2.45.0, і він зламаний: GitHub прибрав старий API, і gh pr view падає з помилкою «GraphQL: Projects (classic) is being deprecated ...» (перевірено 18.11.2026). Документація cli/cli прямо радить офіційні пакети, бо «the community-distributed 2.45.x / 2.46.x version is broken». Встановлення - Урок 02, вхід - Урок 03 (gh auth login).

Нове тут:

  • gh pr view - показує один запит на злиття (PR) за номером. Назва: pr - pull request, «запит на злиття»; view - «переглянути».
  • gh auth login - входить у твій акаунт GitHub, щоб gh міг діяти від тебе. Назва: auth - від authentication, «вхід, підтвердження особи»; login - «увійти».

Передбач, потім запусти

  1. На свіжому ноутбуці, де ще не було gh auth login, запускаєш gh auth status. Що буде?

    Відповідь ```text You are not logged into any GitHub hosts. To log in, run: gh auth login ``` Код виходу 1. gh без входу не має доступу до твоїх репо (вхід - Урок 03).

  2. Ти в домашній теці ~ (не в репо) і пишеш gh issue list. Звідки gh дізнається, чиї Issues показати?

    Відповідь > **Нове тут:** > > - `gh issue list` - показує список завдань (Issues) проєкту на GitHub. Назва: issue - «справа, завдання»; list - «список». Нізвідки - він бере репо з `git remote` поточної теки, а тут репо нема: ```text failed to run git: fatal: not a git repository (or any of the parent directories): .git ``` Або зайди в теку репо, або вкажи репо явно: `gh issue list -R Evge14n/pisochnytsia`.

  3. Друг запускає gh pr checkout 1. Що саме зміниться в його git-репо?

    Відповідь gh скачає гілку PR (`lr2-zavd1`) і перемкне на неї - так само, як `git fetch origin` і `git switch lr2-zavd1`. У `git branch` зʼявиться нова гілка `lr2-zavd1`, яка стежить за `origin/lr2-zavd1`.

Нове тут:

  • git fetch - лише дізнається, що нового на GitHub; твої файли не змінює. origin - звідки (origin - твій GitHub); без нього - теж з origin.
  • git switch - перемикає на іншу гілку (лінію змін); з -c створює нову.
  • git branch - показує, створює і видаляє гілки (окремі лінії змін проєкту).
  1. Ти злив PR кнопкою Squash and merge на сайті і там же натиснув Delete branch (гілки на GitHub більше нема). Потім у терміналі git switch main, git pull, git fetch --prune. Що скаже git branch -d lr2-zavd1?
    Відповідь > **Нове тут:** > > - `git pull` - забирає нові знімки (коміти) з GitHub і одразу додає у твої файли. Назва: pull - «потягнути». > - `git fetch`: `--prune` - прибрати в себе `origin/ГІЛКА`, яких на GitHub уже нема (prune - «обрізати», як садівник гілки). > - `git branch`: `-d` (`--delete`) - видалити гілку, якщо її коміти вже злито (додано в іншу гілку); інакше відмовить (delete - «видалити»). ```text error: the branch 'lr2-zavd1' is not fully merged. If you are sure you want to delete it, run 'git branch -D lr2-zavd1' ``` Код виходу 1, гілка лишилась. Squash робить на `main` **новий** коміт з усіх змін гілки, тож git не бачить у `main` самих комітів гілки. Зміни там є - можна сміливо `git branch -D lr2-zavd1`. (`gh pr merge --delete-branch` прибирає гілку сам.) Якщо ж на сайті **не** натискав Delete branch (або ще не робив `git fetch --prune`), `git branch -d` видалить гілку з попередженням і кодом 0 - див. «Типові помилки», 4.

Руками

Працюємо в пісочниці ~/pisochnytsia на справжньому GitHub (gh не можна «підмінити» локально), тож тут - твій репо Evge14n/pisochnytsia з Уроку 03. Номери Issue і PR у тебе можуть бути інші (якщо вже робив їх в Уроках 10-11) - тоді пиши свої номери замість 1.

Нове тут:

Крок 1. Репо.

cd ~/pisochnytsia

gh repo view --web

Нове тут:

  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • ~ (tilde) - твоя домашня тека, /home/evgen.

gh repo view друкує назву, опис і README. --web і gh browse відкривають сторінку репо в браузері. Ще корисне: gh repo list --limit 5 - пʼять твоїх останніх репо.

Нове тут:

  • gh repo list - показує список твоїх репозиторіїв на GitHub. Назва: repository list - «список репозиторіїв». --limit - скільки репо показати (типово 30), напр. --limit 5 (limit - «межа»).
gh repo list --limit 5

Крок 2. Issue - «завдання собі».

gh issue create --title "ЛР2: перевірити завдання 3" --body "doctest падає на відʼємних числах"
gh issue list
gh issue view 1
gh issue close 1 --comment "Виправлено"
gh issue list --state closed

Нове тут:

  • gh issue create: --title - назва Issue; без неї gh спитає сам (title - «заголовок»); --body - опис Issue (body - «тіло», основний текст).
  • gh issue list: --state - які показати: open (типово), closed - закриті, all - усі (state - «стан»).
  • gh issue view - показує одне завдання (Issue) з GitHub за номером. Назва: issue - «справа, завдання»; view - «переглянути». 1 - номер Issue (видно в gh issue list і в адресі .../issues/1).
  • gh issue close - закриває завдання (Issue) на GitHub за номером. Назва: issue - «справа, завдання»; close - «закрити». --comment - залишити коментар при закритті: --comment "Виправлено" (comment - «коментар»); 1 - номер Issue.
  • "..." (double quotes) - усе між лапками - одне слово, навіть з пробілами.

issue create друкує посилання на нову Issue. --state closed - показати закриті (без нього - лише відкриті).

Крок 3. Pull Request з терміналу. Гілка і коміт - звичайним git (Уроки 07, 09):

git switch -c lr2-zavd1
printf 'def square(number: int) -> int:\n    """\n    >>> square(3)\n    9\n    """\n    return number * number\n' > lr2_1.py
python3 -m doctest lr2_1.py
git add lr2_1.py
git commit -m "ЛР2: завдання 1"
git push -u origin lr2-zavd1

Нове тут:

  • git switch: -c (--create) - створити нову гілку від поточного місця і перейти на неї (create - «створити»).
  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт).
  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати». -m (--message) - повідомлення коміту одразу в команді; без -m відкриється nano (message - «повідомлення»).
  • git push - відправляє твої нові знімки (коміти) з компʼютера на GitHub. Назва: push - «штовхнути». -u (--set-upstream) - запамʼятати пару «моя гілка - гілка на GitHub»; далі просто git push (set upstream - «задати джерело»).
  • printf - друкує текст; \n у ньому - Enter (новий рядок). Назва: print formatted - «надрукувати за шаблоном».
  • '...' (single quotes) - текст буквально: $, * і пробіли всередині - звичайні символи.
  • > (redirect) - пише вивід у файл, старий вміст стирає.
  • python3 - запускає Python: твій файл .py, один рядок коду або вбудований інструмент. Назва: Python - на честь комедійного шоу «Monty Python», 3 - третя версія мови. -m - запусти модуль Python (вбудований чи поставлений через pip) як програму, напр. python3 -m venv (module - «модуль»).
  • python3 -m doctest - перевіряє приклади >>> з опису функцій. Назва: doc test - «тест у документації».

python3 -m doctest нічого не друкує - отже всі тести пройшли. Кінець виводу git push -u:

 * [new branch]      lr2-zavd1 -> lr2-zavd1
branch 'lr2-zavd1' set up to track 'origin/lr2-zavd1'.

Тепер PR:

gh pr create --fill --base main
gh pr list
gh pr view 1
gh pr diff 1

Нове тут:

  • gh pr create: --base - куди зливати: --base main (base - «основа»).
  • gh pr view: 1 - номер PR; без номера - PR поточної гілки.
  • gh pr diff - показує рядки, які змінює запит на злиття (PR). Назва: pr - pull request; diff - від difference, «різниця». 1 - номер PR.

--fill бере назву й опис з комітів (тут - «ЛР2: завдання 1»), --base main - куди зливати. Без --fill gh спитає назву й опис сам. Якщо в описі написати Closes #1, Issue №1 закриється, коли PR зіллють (так пише gh pr create --help).

Нове тут:

  • gh pr create: --help - довідка з усіма прапорцями і прикладами.

Нове тут:

  • gh repo clone: Evge14n/pisochnytsia - ВЛАСНИК/НАЗВА: тут власник Evge14n, репо pisochnytsia; без ВЛАСНИК/ gh візьме твій акаунт.

Що gh pr checkout 1 робить усередині: якби gh не було, замість нього (не після) у ~/druhyi-klon можна руками (тут не набирай - це лише для розуміння):

Крок 5. Злити PR (ти в ~/pisochnytsia, на гілці lr2-zavd1):

gh pr merge 1 --squash --delete-branch
git log --oneline -n 3

Нове тут:

  • git log - показує історію комітів, новий зверху. --oneline - по рядку на коміт: 7 знаків хешу і перший рядок повідомлення; -n (--max-count) - лише N останніх комітів: -n 3 (або коротко -3) (number - «число»).

--squash - усі коміти PR стають одним комітом на main (Урок 11, види merge). --delete-branch - видалити гілку і на GitHub, і в тебе. Якщо ти стояв на цій гілці, gh перемкне тебе на main і зробить git pull (так написано в коді gh 2.105, pkg/cmd/pr/merge/merge.go). У виводі будуть рядки за шаблоном ✓ Squashed and merged pull request Evge14n/pisochnytsia#1 (...), ✓ Deleted local branch lr2-zavd1 and switched to branch main, ✓ Deleted remote branch lr2-zavd1 (шаблон з коду, на справжньому GitHub у цьому курсі не запускали). git log --oneline -n 3 покаже на main новий коміт з назвою PR.

Довідка, коли забув прапорець:

gh help
gh pr merge --help

Повна довідка онлайн: https://cli.github.com/manual

Типові помилки

  1. Не увійшов. gh auth status → You are not logged into any GitHub hosts. To log in, run: gh auth login (код 1), а будь-яка робоча команда, наприклад gh issue list: text To get started with GitHub CLI, please run: gh auth login Alternatively, populate the GH_TOKEN environment variable with a GitHub API authentication token. Код виходу 4. Виправлення: gh auth login (Урок 03).

  2. Не в теці репо. failed to run git: fatal: not a git repository (or any of the parent directories): .git. Зайди в репо (cd ~/pisochnytsia) або вкажи репо прапорцем: bash gh issue list -R Evge14n/pisochnytsia

Нове тут:

  • gh issue list: -R (--repo) - інший репо: -R Evge14n/pisochnytsia, а не з поточної теки (repo - «репо»).

  1. Старий gh з репо Mint. gh pr view падає з GraphQL: Projects (classic) is being deprecated ..., а gh --version показує 2.45.0. Видали його і постав з офіційного репо (Урок 02).

  2. Злив на сайті кнопкою Squash and merge і видалив там гілку (Delete branch) - git branch -d не видаляє. Після git switch main, git pull і git fetch --prune: text error: the branch 'lr2-zavd1' is not fully merged. If you are sure you want to delete it, run 'git branch -D lr2-zavd1' Переконайся, що PR справді злито (на сторінці PR фіолетова позначка Merged, або gh pr view 1), і видали з -D: bash git branch -D lr2-zavd1

Нове тут:

  • git branch: -D - видалити навіть незлиту гілку; її коміти зникнуть з видимості (велика D - delete силою).

Незвичне (git 2.43): якщо гілка origin/lr2-zavd1 у тебе ще є - на сайті не натискав Delete branch, або натискав, але git fetch --prune ще не робив, - то git branch -d гілку видаляє (код 0), лише з попередженням: text warning: deleting branch 'lr2-zavd1' that has been merged to 'refs/remotes/origin/lr2-zavd1', but not yet merged to HEAD Deleted branch lr2-zavd1 (was 3c4bd53). Бо -d порівнює з гілкою, за якою твоя стежить (origin/lr2-zavd1), а не лише з main.

Як роблять профі

  • PR з Issue одним рухом: gh pr create --fill + у тексті Closes #12 - після злиття Issue закриється сама.
  • Рев'ю з терміналу: gh pr checkout 7 → запустити тести → gh pr review 7 --approve або gh pr review 7 --request-changes --body "..." (cli.github.com/manual/gh_pr_review).
  • Стежити за Actions (той самий «pages build and deployment» з Уроку 15) без браузера: bash gh run list --limit 3

Нове тут:

  • gh run list - показує останні автоперевірки на GitHub (запуски GitHub Actions). Назва: run list - «список запусків» (GitHub Actions). --limit - скільки запусків показати (типово 20), напр. --limit 3.
  • Опублікувати локальний репо одним рядком: gh repo create univer-labs --private --source=. --remote=origin --push (створює репо на GitHub, додає origin і пушить; файл «Лаби в git»).
  • gh api - будь-який запит до GitHub API для скриптів, напр. gh api repos/Evge14n/uni-prep (cli.github.com/manual/gh_api).

Нове тут:

  • gh repo create: --source - взяти теку, що вже є на ноутбуці, напр. --source=. - поточну (source - «джерело»); --remote - під яким іменем git памʼятатиме адресу репо на GitHub, зазвичай --remote=origin (remote - «віддалений»); --push - одразу відправити коміти з --source на GitHub (push - «штовхнути»).
  • gh api - робить будь-який запит до GitHub напряму (API, для скриптів). Назва: API - application programming interface, «інтерфейс для програм». repos/Evge14n/uni-prep - шлях запиту: відомості про репо Evge14n/uni-prep.

Самоперевірка

  1. Чим відрізняється робота git і gh?
  2. Звідки gh pr list знає, з яким репо працювати, і як вказати інше?
  3. Якою командою створити PR з поточної гілки в main, взявши назву з комітів?
  4. Що роблять прапорці --squash і --delete-branch у gh pr merge?
  5. Чому gh ставлять з офіційного репо GitHub, а не з Менеджера програм Mint?
Відповіді
  1. git - коміти, гілки, push/pull з репозиторієм. gh - сайт GitHub: Issues, PR, налаштування, Actions (через API).
  2. З git remote поточної теки. Інше репо - -R Evge14n/НАЗВА.
  3. gh pr create --fill --base main.
  4. --squash - усі коміти PR одним комітом на main; --delete-branch - видалити гілку на GitHub і локально (і перемкнути тебе на main).
  5. У репо Mint gh 2.45.0, він зламаний (GitHub прибрав старий API). Офіційний пакет новий і оновлюється разом із системою.
