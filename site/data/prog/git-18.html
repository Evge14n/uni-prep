Тема 18. Лаби в git - univer-labs покроково

Навіщо: усі сім лаб - в одному приватному репо на GitHub. Кожне завдання, що пройшло doctest, - окремий коміт (зіпсуєш - повернешся). Кожна лаба - своя гілка. Кожна здача - тег. Викладачу - посилання або архів одною командою.

Перед цим файлом: Уроки 04-09 (коміти, гілки, push), 11 (PR), 14 (теги). Робоче місце - як у курсі Linux Mint: теки ~/univer/labs/lr1 ... ~/univer/labs/lr7, venv ~/univer/.venv (він поза репо - так і має бути). На GitHub і в повідомленнях комітів лаби звемо «ЛР1» ... «ЛР7», а теки й гілки - латиницею lr1 ... lr7 (латиницю простіше набирати в терміналі).

Як усе влаштовано

GitHub: Evge14n/univer-labs (ПРИВАТНИЙ)                ноутбук: ~/univer/labs
  main ──●──────●───────────●──── ...                    .gitignore   README.md
         │      │ lr1-zdano │ lr2-zdano                  lr1/  lr1_1.py  lr1_2.py  lr1_3.py
         │      │           │                            lr2/  ...
  lr1    └─●─●─●┘           │                            ...
  lr2           └──●──●─────┘   (гілка на лабу,          lr7/
                                 коміт на завдання)
  • Один репо на всі лаби, бо так простіше: один git push, одна історія, один .gitignore.
  • Гілка lr1 живе, поки робиш ЛР1. main - лише завершені лаби.
  • Коміт - після кожного завдання, що пройшло doctest (і перед великою правкою, наприклад black).
  • Тег lr1-zdano - на коміті, який показав викладачу (Урок 14).

Виводи нижче - справжні, з перевірки (git 2.43.0). Хеші комітів у тебе будуть інші. Ярлики в дужках, як-от (HEAD -> lr1, origin/lr1), git друкує в терміналі: де стоїш ти (HEAD), де твої гілки і де гілки на GitHub (origin/...).

Один раз: репо univer-labs

Крок 1. Чи є вже git у теці лаб? Якщо ти робив Крок 8 Уроку 04 курсу Linux Mint, git там уже є.

cd ~/univer/labs
git status

Нове тут:

  • cd - переходить в іншу теку. Назва: change directory - «змінити теку».
  • git status - показує, що змінено і що піде в наступний коміт. Назва: status - «стан».
  • ~ - домашня тека /home/evgen. Назва: tilde («тильда») - домашня тека.

Усе про кожну команду - у вкладці «Команди», а тут торкнись команди в коді - вискочить підказка. Якщо бачиш fatal: not a git repository (or any of the parent directories): .git - git нема, йди у варіант А. Якщо бачиш On branch ... - git є, йди у варіант Б.

Крок 2. Порожній приватний репо на GitHub. Два способи, обери один: - на сайті (зроби зараз): справа вгорі + → New repository → Repository name: univer-labs → Private → README, .gitignore, license не додавай (репо має бути порожнім, інакше перший push відхилять - див. «Що як» 5) → Create repository; - через gh - тоді на сайті нічого не створюй і цей крок пропусти: репо створить gh repo create у кінці варіанта (див. нижче, після варіанта А). Потрібен вхід у gh (Урок 03, крок 6 Шляху А або Шлях Б).

Варіант А - git ще нема.

mkdir -p ~/univer/labs/lr1
cd ~/univer/labs
git init
printf '.venv/\n__pycache__/\n*.pyc\n.pytest_cache/\n.mypy_cache/\n.ruff_cache/\n' > .gitignore
printf '# Лабораторні з програмування\n\nЛР1-ЛР7, 1 курс. Кожна лаба - тека lrN і тег lrN-zdano.\n' > README.md
git add .gitignore README.md
git commit -m "Початок: .gitignore і README"
git remote add origin git@github.com:Evge14n/univer-labs.git
git push -u origin main

To github.com:Evge14n/univer-labs.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

Нове тут:

  • mkdir - створює нову теку. Назва: make directory - «зробити теку». -p - створює і всі проміжні теки шляху; якщо тека вже є - мовчить, без помилки.
  • git init - робить теку репозиторієм git (створює .git). Назва: init - від initialize, «почати, підготувати».
  • printf - друкує текст за шаблоном; \n - Enter. Назва: print formatted - «надрукувати за шаблоном».
  • git add - додає зміни файлу в наступний коміт (індекс). Назва: add - «додати» (в індекс, тобто в наступний коміт).
  • git commit - зберігає знімок змін з індексу в історію. Назва: commit - «зафіксувати»: зберегти знімок змін в історію. -m - повідомлення коміту одразу в команді; без -m відкриється nano.
  • git remote - показує і задає адресу репо на GitHub (origin). Назва: remote - «віддалений»: репо на іншому компʼютері (GitHub). origin - звичайна назва головного віддаленого репо; git clone ставить її сам.
  • git push - відправляє твої коміти на GitHub. Назва: push - «штовхнути»: відправити свої коміти на GitHub. -u - запамʼятати звʼязок гілки з GitHub; далі просто git push і git pull.
  • '...' - текст буквально, нічого не підставляється. Назва: одинарні лапки - «буквально, як написано».
  • > - пише вивід у файл, старий вміст стирає. Назва: redirect - «перенаправлення» виводу у файл.
  • "..." - текст з пробілами одним словом, $ підставляється. Назва: подвійні лапки - «усе це одне слово, але $ працює». .gitignore (Урок 06): .venv/ - віртуальне середовище, __pycache__/ і *.pyc - скомпільований Python, .pytest_cache/, .mypy_cache/, .ruff_cache/ - сміття від pytest, mypy і ruff.

Якщо в Кроці 2 обрав gh (репо на сайті ще нема): замість двох останніх рядків (git remote add ... і git push -u ...) набери один - gh (Урок 16) створить приватний репо, додасть origin і запушить. Так само і в кінці варіанта Б. Якщо репо univer-labs на сайті вже створив, gh другого з тією самою назвою не створить - тоді просто git remote add і git push -u, як вище.

gh repo create univer-labs --private --source=. --remote=origin --push

Нове тут:

  • gh repo create - створює репозиторій на GitHub з терміналу. Назва: repository create - «створити репозиторій» на GitHub. --private - приватний репо: бачиш лише ти (і кого запросиш); для лаб - саме так; --source - взяти теку, що вже є на ноутбуці, напр. --source=. - поточну; --remote - як назвати віддалений репо в git, напр. --remote=origin; --push - одразу запушити коміти з --source на GitHub.

Варіант Б - git уже є (з курсу Linux Mint). Подивись, що там:

git log --oneline
git branch --show-current

Нове тут:

  • git log - показує історію комітів, новий зверху. Назва: log - «журнал»: історія комітів. --oneline - по рядку на коміт: 7 знаків хешу і перший рядок повідомлення.
  • git branch - показує, створює і видаляє гілки. Назва: branch - «гілка». --show-current - надрукувати лише назву гілки, на якій ти зараз. Якщо гілка називається master (git до налаштування з Уроку 02 так називав першу гілку) - перейменуй:
git branch -m master main

Нове тут:

  • git branch: -m - перейменувати гілку: git branch -m master main. У .gitignore з курсу Linux Mint нема .venv/ і *.pyc - допиши (>> дописує в кінець, > перезаписав би):
printf '.venv/\n*.pyc\n' >> .gitignore
git add .gitignore
git commit -m "gitignore: .venv і *.pyc"
git remote add origin git@github.com:Evge14n/univer-labs.git
git push -u origin main

Нове тут:

  • >> - дописує вивід у кінець файлу. Назва: append - «дописати» в кінець файлу. Старі коміти ЛР1 так і лишаться на main - це нормально, гілки починай з наступної лаби.

На кожну лабу - рецепт

git switch main && git pull                     # свіжий main
git switch -c lrN                               # гілка лаби
  (заготовка в lrN/)  git add lrN  git commit -m "ЛРN: заготовки викладача"
  повтор на кожне завдання:
    nano lrN/lrN_K.py  →  doctest пройшов  →  git commit -am "ЛРN: завдання K"
git push -u origin lrN                          # копія на GitHub (і для PR)
злиття в main: або git switch main + git merge lrN + git push,
               або PR на GitHub (gh pr create --fill --base main) і Merge
git tag -a lrN-zdano -m "ЛРN здано" main  +  git push origin lrN-zdano     # коли здав

Чому спершу коміт заготовки: тоді git diff завжди покаже, що саме ти змінив у файлі викладача, а викладач забороняє міняти назви функцій, параметри і doctest заготовки (див. «Вимоги викладача»).

ЛР1 від гілки до архіву

Гілка і заготовки. Заготовки поклади в ~/univer/labs/lr1/ так, як у курсі Linux Mint (Урок 04 - з .ipynb).

git switch main
git pull
git switch -c lr1
git add lr1
git commit -m "ЛР1: заготовки викладача"

Нове тут:

  • git switch - перемикає на іншу гілку (-c - створює нову). Назва: switch - «перемкнути». -c - створити нову гілку від поточного місця і перейти на неї.
  • git pull - забирає нові коміти з GitHub і зливає у твою гілку. Назва: pull - «потягнути»: забрати нові коміти з GitHub до себе.

Завдання 1. Пишеш код, перевіряєш doctest, комітиш.

nano lr1/lr1_1.py
python3 -m doctest lr1/lr1_1.py
git status --short
git commit -am "ЛР1: завдання 1"

Нове тут:

  • nano - простий редактор файлів у терміналі. Назва: nano - жарт з одиницями: наступник редактора pico (піко < нано).
  • python3 - запускає Python: файл, рядок коду або модуль. Назва: Python - на честь комедійного шоу «Monty Python», 3 - третя версія мови. -m - запусти модуль як програму: python3 -m pytest, python3 -m venv, python3 -m pdb.
  • python3 -m doctest - перевіряє приклади >>> з опису функцій. Назва: doc test - «тест у документації»: приклади >>> в описі функції.
  • git status: --short - коротко: по рядку на файл з двома буквами стану (M, A, ??).
  • git commit: -a - спершу сам додає зміни ВЖЕ відстежуваних файлів; нові файли - ні. python3 -m doctest нічого не друкує - отже всі тести пройшли (для лаб з input() бери команду з розділу «Перевір перед здачею» курсу Linux Mint). git status --short має показати лише M lr1/lr1_1.py: тека lr1/__pycache__, яку створив Python, не видна - її ховає .gitignore.

Завдання 2 - так само:

nano lr1/lr1_2.py
python3 -m doctest lr1/lr1_2.py
git commit -am "ЛР1: завдання 2"
git push -u origin lr1
git log --oneline main..lr1

676c781 (HEAD -> lr1, origin/lr1) ЛР1: завдання 2
ac98c9d ЛР1: завдання 1
09e5e28 ЛР1: заготовки викладача

Нове тут:

  • git log: main..lr1 - коміти, що є в гілці lr1, але ще нема в main. main..lr1 - коміти, які є в lr1, але ще нема в main. git push -u origin lr1 - копія гілки на GitHub: ноутбук зламався - лаба ціла. Ярлик origin/lr1 на верхньому коміті це й показує: на GitHub гілка lr1 там само.

Лабу закінчено - у main. Найпростіше - злиття в себе (Урок 07):

git switch main
git merge lr1
git push
git branch -d lr1

Нове тут:

  • git merge - зливає іншу гілку в поточну. Назва: merge - «злити, обʼєднати».
  • git branch: -d - видалити гілку, якщо її коміти вже злито; інакше відмовить. git merge скаже Fast-forward: main просто наздогнав lr1. Гілку lr1 можна видалити - її коміти тепер у main (на GitHub вона ще є, її видалиш кнопкою на сторінці гілок або git push origin --delete lr1).

Здав - тег (Урок 14):

git tag -a lr1-zdano -m "ЛР1 здано"
git push origin lr1-zdano

To github.com:Evge14n/univer-labs.git
 * [new tag]         lr1-zdano -> lr1-zdano

Нове тут:

  • git tag - ставить на коміт мітку з назвою (напр. lr1-zdano). Назва: tag - «мітка, ярлик». -a - анотований тег: з автором, датою і описом (для здачі - саме такий); -m - опис анотованого тегу; без -m git відкриє nano.

ЛР2 через Pull Request

Те саме, але злиття - через PR (Урок 11): видно всі зміни лаби на одній сторінці, можна попросити одногрупника глянути.

git switch main
git pull
git switch -c lr2
mkdir -p lr2
nano lr2/lr2_1.py
python3 -m doctest lr2/lr2_1.py
git add lr2/lr2_1.py
git commit -m "ЛР2: завдання 1"
git push -u origin lr2
gh pr create --fill --base main

Нове тут:

  • gh pr create - створює Pull Request з поточної гілки. Назва: pr - pull request, «запит на злиття» гілки в main; create - «створити». --fill - назву й опис узяти з комітів гілки; --base - куди зливати: --base main. У nano - код завдання з doctest (тут для короткості одне завдання; у справжній ЛР2 спершу поклади заготовки викладача і закоміть їх, як у ЛР1). gh pr create працює лише після входу в gh (Урок 03, крок 6), інакше скаже To get started with GitHub CLI, please run: gh auth login. Без gh: на сторінці репо зʼявиться жовта смуга з кнопкою Compare & pull request (Урок 11). На сторінці PR → Merge pull request → Confirm merge. Потім у себе:
git switch main
git pull
git log --oneline --graph -n 3
git tag -a lr2-zdano -m "ЛР2 здано" main
git push origin lr2-zdano

*   0e746e0 (HEAD -> main, origin/main) Merge pull request #1 from Evge14n/lr2
|\
| * 90a7770 (origin/lr2, lr2) ЛР2: завдання 1
|/
* 676c781 (tag: lr1-zdano, origin/lr1) ЛР1: завдання 2

Нове тут:

  • git log: --graph - малює гілки зліва зірочками і лініями; -n - лише N останніх комітів: -n 3 (або коротко -3). Після злиття PR сайт пропонує кнопку Delete branch. Навіть якщо натиснув її, origin/lr2 у тебе ще видно: git pull не прибирає гілки, яких на GitHub уже нема (прибере git fetch --prune). tag: lr1-zdano - здача ЛР1. main у кінці рядка з тегом - тег саме на main, навіть якщо ти вже на іншій гілці. Список здач:
git tag -n

lr1-zdano       ЛР1 здано
lr2-zdano       ЛР2 здано

Нове тут:

  • git tag: -n - у списку тегів показати й перший рядок опису.

Як показати викладачу

Спосіб 1. Посилання на репо. Приватний репо бачать лише запрошені. Запросити: у репо Settings → розділ «Access» → Collaborators → Add people → логін викладача → Add ... to univer-labs. Йому прийде лист, доступ буде після того, як він прийме запрошення (docs.github.com, «Inviting collaborators to a personal repository», відкрито 18.11.2026). Увага: у приватному репо особистого акаунта співавтор отримує доступ на запис: «repository owners can only grant write access to collaborators. Collaborators can't have read-only access» (docs, «Permission levels for a personal account repository»). Тобто викладач зможе і пушити. Після семестру прибери доступ там само (Collaborators → Remove). Посилання на конкретну здачу: https://github.com/Evge14n/univer-labs/tree/lr1-zdano/lr1.

Спосіб 2. Архів zip - коли викладач хоче файли (вимога з консультації: тека з назвою «прізвище, ім'я, група, рік»; точний формат архіву уточни на парі). git archive бере файли з тегу, а не з теки на диску, тому в архів потрапляє рівно здана версія і лише те, що в git: без .venv, __pycache__, .pytest_cache.

mkdir -p ~/univer/zdacha
git archive --format=zip --prefix=Прізвище_Імʼя_Група_2026/ -o ~/univer/zdacha/lr1.zip lr1-zdano lr1
python3 -m zipfile -l ~/univer/zdacha/lr1.zip

File Name                                             Modified             Size
Прізвище_Імʼя_Група_2026/                    2026-11-18 10:35:20            0
Прізвище_Імʼя_Група_2026/lr1/                2026-11-18 10:35:20            0
Прізвище_Імʼя_Група_2026/lr1/lr1_1.py        2026-11-18 10:35:20          114
Прізвище_Імʼя_Група_2026/lr1/lr1_2.py        2026-11-18 10:35:20          105

Нове тут:

  • git archive - пакує файли з коміту чи тегу в zip або tar. Назва: archive - «архів». --format - zip або tar; без нього - за розширенням файлу після -o, інакше tar; --prefix - покласти все в архіві в цю теку: --prefix=Prizvyshche_Imia/ (з / в кінці); -o - куди записати архів; тека має вже існувати.
  • python3 -m zipfile - робить і розпаковує .zip засобами Python. Назва: zipfile - модуль стандартної бібліотеки Python, запущений як програма (-m). -l - показати вміст: назви, дати, розміри. Що тут що: --format=zip - zip, а не tar; --prefix=.../ - тека, в яку все покладуть усередині архіву (скісна риска в кінці обовʼязкова); -o - куди писати архів; lr1-zdano - з якого тегу брати; lr1 - лише ця тека, а не весь репо. Перевірено: у тій самій теці на диску лежали .venv/, lr1/__pycache__/, lr1/.pytest_cache/ - в архів не потрапило нічого з цього, і .gitignore теж. Кирилиця в назвах збережена з UTF-8-позначкою zip. python3 -m zipfile -l показує вміст архіву (окремої програми unzip не треба). Для ЛР2:
git archive --format=zip --prefix=Прізвище_Імʼя_Група_2026/ -o ~/univer/zdacha/lr2.zip lr2-zdano lr2

Спосіб 3. «Download ZIP» на сайті. У репо → Releases → вгорі Tags → біля lr1-zdano посилання zip (docs, «Downloading source code archives»). Це архів усього репо на момент тегу (усі лаби до тієї, і README), а тека всередині названа за назвою репо - тож для здачі однієї лаби зручніший git archive.

Що як ...

1. Почав лабу на main без гілки (кілька комітів, ще не пушив). git status каже Your branch is ahead of 'origin/main' by 2 commits. Перенеси коміти в гілку і поверни main назад:

git switch -c lr3
git branch -f main origin/main
git log --oneline main..lr3

branch 'main' set up to track 'origin/main'.
10107b7 (HEAD -> lr3) ЛР3: завдання 2
549cce4 ЛР3: завдання 1

Нове тут:

  • git branch: -f - переставити гілку на інший коміт: git branch -f main origin/main. git switch -c lr3 - нова гілка там, де ти стоїш, з усіма комітами. git branch -f main origin/main - «постав main туди, де він на GitHub»; файли не чіпає, бо ти вже на lr3. Перший рядок виводу - не помилка: git заодно нагадує, що main стежить за origin/main. Якщо ж забудеш перейти на lr3, git не дасть пересунути поточну гілку: fatal: cannot force update the branch 'main' used by worktree at '...' (далі - шлях до твоєї теки). Якщо коміти на main уже запушив - не виправляй історію силою; просто продовжуй, наступну лабу почни з гілки.

2. Забув поставити тег, а вже робиш наступну лабу. Тег можна поставити заднім числом на будь-який коміт:

git tag -a lr2-zdano -m "ЛР2 здано" main
git push origin lr2-zdano

Якщо main уже пішов далі, знайди потрібний коміт у git log --oneline і постав тег на його хеш:

git tag -a lr2-zdano -m "ЛР2 здано" ХЕШ

3. Закомітив .venv (або __pycache__). Прибери з git, лишивши на диску:

git rm -r -q --cached .venv
git commit -m "Прибери .venv з git"
git ls-files .venv
git check-ignore -v .venv

.gitignore:1:.venv/ .venv

Нове тут:

  • git rm - прибирає файл з git (з --cached - файл лишається на диску). Назва: rm - від remove, «прибрати». -r - рекурсивно: щоб прибрати цілу теку з усім вмістом; -q - не друкувати рядок rm '...' на кожен файл; --cached - прибрати лише з git (з індексу), файл на диску лишається.
  • git ls-files - перелічує файли, які відстежує git. Назва: ls files - «перелічити файли» (ls - від list, «список»). .venv - лише файли в цій теці: порожньо - тека в git не потрапила (так і треба).
  • git check-ignore - перевіряє, чи файл ігнорується і яким правилом .gitignore. Назва: check ignore - «перевірити, чи ігнорується». -v - показати правило: файл .gitignore, номер рядка, шаблон і шлях. --cached - лише з git, файли на диску лишаються. -q (тихо) - без нього git друкує рядок rm '.venv/...' на кожен файл, а в справжньому .venv їх тисячі. git ls-files .venv після цього нічого не друкує. git check-ignore -v показує, яке правило .gitignore тепер ховає .venv: файл, номер рядка, правило. У варіанті А правило в рядку 1; у варіанті Б ти дописав його в кінець, тож номер буде інший (у перевірці - .gitignore:5:). Якщо в .gitignore правила нема - спершу допиши його (printf '.venv/\n*.pyc\n' >> .gitignore, варіант Б). Старі коміти з .venv в історії лишаться - для лаб це лише зайвий розмір, не біда.

4. Не знаєш, що ти змінив після здачі: git diff lr1-zdano main -- lr1 (Уроки 05, 14).

5. Створив репо на сайті З README - перший push відхилено. Варіант А, але в Кроці 2 увімкнув «Add README». Тоді git push -u origin main каже:

To github.com:Evge14n/univer-labs.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:Evge14n/univer-labs.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

На GitHub є коміт з README, якого нема в тебе. Підказка радить git pull, але простий git pull тут не зіллє:

From github.com:Evge14n/univer-labs
 * [new branch]      main       -> origin/main
There is no tracking information for the current branch.
Please specify which branch you want to merge with.
See git-pull(1) for details.

    git pull <remote> <branch>

If you wish to set tracking information for this branch you can do so with:

    git branch --set-upstream-to=origin/<branch> main

Чому: push відхилено, тож і -u не спрацював - main ще не знає, що стежить за origin/main. Тому треба сказати явно, звідки тягнути: git pull origin main. Але й так git відмовить: fatal: refusing to merge unrelated histories - у твоєї історії і в історії на сайті нема жодного спільного коміту. Дозволь злиття явно:

git pull --allow-unrelated-histories origin main

From github.com:Evge14n/univer-labs
 * branch            main       -> FETCH_HEAD
Auto-merging README.md
CONFLICT (add/add): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

Нове тут:

  • git pull: --allow-unrelated-histories - дозволити злити дві історії без спільного початку (репо на сайті створили з README). add/add - файл README.md додали з двох боків (ти у своєму коміті і сайт у своєму), і текст різний. Розвʼязуєш як в Уроці 08: відкрий файл, лиши потрібний текст і прибери три рядки-маркери:
nano README.md

<<<<<<< HEAD
# Лабораторні з програмування

ЛР1-ЛР7, 1 курс. Кожна лаба - тека lrN і тег lrN-zdano.
=======
# univer-labs
>>>>>>> acb504200d89530b7a396bf8da830c49922532b6

Згори (HEAD) - твій README, знизу - README з сайту (там може бути ще рядок з описом репо), після >>>>>>> - хеш коміту з сайту. Лиши свої три рядки, видали <<<<<<< HEAD, =======, # univer-labs і >>>>>>> ..., збережи (Ctrl+O, Enter, Ctrl+X). Далі:

git add README.md
git commit
git push -u origin main

git commit без -m відкриє nano з готовим повідомленням Merge branch 'main' of github.com:Evge14n/univer-labs - лиши як є, Ctrl+X. Тепер push проходить і заодно ставить стеження:

To github.com:Evge14n/univer-labs.git
   c292ff6..a91a74b  main -> main
branch 'main' set up to track 'origin/main'.

Відтепер працює і простий git pull. У варіанті Б README зазвичай лише на сайті - тоді конфлікту нема: git pull --allow-unrelated-histories origin main одразу зливає (Merge made by the 'ort' strategy.), nano пропонує повідомлення злиття - Ctrl+X, потім git push -u origin main.

Для лаб - цей файл і є «для лаб»: ЛР1-ЛР7 за одним рецептом, викладачу - посилання або архів з тегу.

Самоперевірка

  1. Чому один приватний репо univer-labs, а не публічний, і чому не сім окремих?
  2. Коли робити коміт під час лаби і навіщо перший коміт - із заготовкою?
  3. Ти закінчив ЛР3 на гілці lr3. Які команди - злити в main, поставити тег здачі і відправити все на GitHub?
  4. Чому в архіві git archive ... lr1-zdano lr1 нема .venv і __pycache__, хоч вони лежать у теці?
  5. Ти дав викладачу доступ Collaborator до приватного репо. Що він може робити і що зробити після семестру?
Відповіді
  1. Приватний - бо розвʼязки до здачі не мають бачити одногрупники. Один - бо простіше: один .gitignore, один push, уся історія лаб разом; лаби розділяють теки lr1...lr7, гілки і теги.
  2. Після кожного завдання, що пройшло doctest (і перед великою правкою). Перший коміт із заготовкою - щоб git diff показував, що саме ти змінив у файлі викладача.
  3. git switch main, git merge lr3, git push, git tag -a lr3-zdano -m "ЛР3 здано", git push origin lr3-zdano (або PR на GitHub, потім git pull і тег).
  4. git archive бере файли з коміту під тегом, а в коміти вони не потрапляють - їх ховає .gitignore.
  5. Читати і пушити: у приватному репо особистого акаунта доступ співавтора лише «на запис». Після семестру - Settings → Collaborators → Remove.
